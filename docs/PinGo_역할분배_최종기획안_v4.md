## 1. 역할 분배 목표

이번 역할 분배는 단순히 기능 개수를 비슷하게 나누는 것이 아니라 다음 기준으로 운영한다.

1. 기능마다 최종 책임자를 한 명만 둔다.
2. 도메인·코드·테스트·문서의 소유권을 함께 배정한다.
3. 기능 요구사항 32개를 모두 8월 9일까지 FR-Done으로 완료한다.
4. 세 백엔드 담당자 모두 핵심 제품 기능을 직접 소유한다.
5. 인프라·지원 업무만 담당하는 사람이 생기지 않도록 한다.
6. 화면이나 API만 구현된 상태는 완료로 인정하지 않는다.
7. 담당자는 정상 흐름뿐 아니라 실패·복구 흐름까지 책임진다.

백엔드 담당은 다음 세 축으로 분리한다.

- **신재령**: 공간 데이터·경로 탐색·AI 결과 좌표 앵커링
- **오서현**: 인증·상담 상태·WebRTC signaling·DataChannel
- **이정우**: 위치추정 AI Adapter(상태판정·circuit breaker)·외부 연계·인프라

> **주의**: 신재령는 AI 모델이나 AI 서버를 직접 다루지 않는다. AI 서버 호출·응답 검증·상태판정·circuit breaker는 전부 이정우 소유다. A는 이미 검증이 끝난 좌표를 지도 좌표계·유효 노드로 변환하는 작업만 한다. 이 경계를 "A=AI"로 뭉뚱그려 부르지 않는다.

기존의 Phase 1·조건부 Phase 2 구분은 사용하지 않는다.

- 정식 기능 요구사항 32개 모두 필수 범위다.
- 기능 제외·조건부 착수·미완료 철회는 허용하지 않는다.
- 기능명세서에 없는 신규 기능은 8월 9일 이후 백로그로 보낸다.

## 지원 담당자

지원 담당자는 인터페이스 연동·화면 구현·테스트·리뷰에 참여하지만 최종 완료 판정을 대신하지 않는다.

## FR-Done 완료 기준

다음 조건을 모두 충족해야 FR-Done으로 인정한다.

- 기능명세서의 세부 요구사항이 모두 구현됐다.
- 실제 API·AI·데이터·네트워크와 연결됐다.
- 정상·로딩·빈 데이터·오류 상태를 처리한다.
- 권한 거부·네트워크 실패·AI 실패 흐름을 처리한다.
- 지정된 인수조건을 통과했다.
- 실제 기기 또는 실제 브라우저 테스트를 통과했다.
- MR이 `develop`에 병합됐다.
- Jira에 테스트 결과·화면·영상·로그 중 하나 이상의 증거가 첨부됐다.
- 기능명세서·API·ERD·이벤트 문서가 코드와 일치한다.

다음 상태는 FR-Done으로 인정하지 않는다.

- 화면만 구현된 상태
- API만 구현된 상태
- Mock 또는 Fixture만 연결된 상태
- 정상 흐름만 동작하고 실패 흐름이 없는 상태
- 테스트 증거 없이 담당자가 구두로 완료했다고 보고한 상태

# 5. 강민수 — AI·Visual Localization

## 최종 책임

역삼역 대표 동선의 이미지에서 사용자 위치·방향·신뢰도를 계산하고, 맵 구축 데이터와 분리된 평가 데이터로 위치추정 성능을 검증한다.

VPS가 실패할 경우 사용할 최소 1개 이상의 보조 위치 인식 방법을 완성한다.

## 최종 책임 FR

- `FR-V-001` VPS 데이터 구축
- `FR-V-002` 보조 위치 인식

## 데이터 구축

- 촬영 동선·간격·각도 정의
- 영상·이미지 품질 기준
- 통제 공간 촬영
- 실제 역사 촬영
- 프레임 추출
- 맵 구축 데이터와 평가 데이터 분리
- 얼굴·개인정보 포함 데이터 처리 기준
- 원본 보관·삭제 기준
- 주요 지점별 위치 인식 성공·실패 기록

## AI 파이프라인

- COLMAP 기반 3D Map

```text
REQUESTED
WAITING
ACCEPTED
REJECTED
CANCELED
EXPIRED
NO_COUNSELOR
```

대기 화면으로 전달하는 주요 이벤트는 다음과 같다.

```text
CONSULTATION_REQUESTED
CONSULTATION_ACCEPTED
CONSULTATION_REJECTED
CONSULTATION_CANCELED
CONSULTATION_EXPIRED
NO_COUNSELOR_AVAILABLE
```

- 최대 대기 시간과 요청 만료 시간을 설정한다.
- 여러 상담자가 동시에 수락한 경우 한 명만 성공하도록 동시성을 제어한다.
- 사용자가 새로고침하거나 재접속해도 자신의 요청 상태를 다시 조회할 수 있어야 한다.
- 상담자 온라인 상태는 `OFFLINE`, `AVAILABLE`, `BUSY`, `AWAY`, `DISABLED`로 관리한다.
- WebSocket 종료 시 자동 상태 보정, 상담 수락 시 `BUSY`, 종료 시 `AVAILABLE` 복귀를 처리한다.

# 13. 역할 분배 실질 부담 검증 노트 (v2 신규)

FR 개수(A 8 / B 8 / C 4)만 보면 균형 있어 보이지만, 두 가지 보정 요인을 겹쳐보면 실질 부담 순서가 달라질 수 있다.

## 13.1 신재령 — 외부 공공데이터로 경감될 가능성

서울시 공공데이터(지하철역 연계 지하도 공간정보, 지하철역 엘리베이터/출입구 리프트 위치정보, 역사마스터 정보)를 확보하면, FR-A-003(시설·출구 관리)·FR-A-004(경로 관리)의 seed data 작업이 수작업 측량·트레이싱에서 데이터 파싱·변환(ETL)으로 상당 부분 대체될 수 있다. 이 데이터는 이미 WGS84 좌표 기반 노드-링크 그래프 형태이고 링크 길이가 사전 계산돼 있어, A의 route_node/route_edge 테이블과 구조적으로 거의 일치한다.

**리스크**: 이 데이터 확보는 공개데이터 신청 절차(승인 대기 필요)에 달려 있어 100% 확정이 아니다. 1주차 말까지 확보 여부를 확인하고, 확보되면 A의 여유 시간을 어디로 돌릴지 미리 합의해둔다.

## 13.2 이정우 — AI Adapter 복잡도로 실질 부담이 FR 개수보다 큼

FR 개수는 4개로 가장 적지만, `AI Adapter` 안에 담긴 작업(AI 응답 DTO 검증, 7단계 상태판정 로직, circuit breaker, 재시도+backoff)은 설계 복잡도가 높다. 11장에서 이미 이를 인지하고 "단순 인프라 담당으로 판단하지 않는다"고 명시해두었다.

## 13.3 오서현 — 두 보정 요인의 수혜가 없음

A는 외부데이터로 경감될 여지가 있고, C는 FR 개수 대비 부담이 이미 별도로 인지·문서화돼 있다. 반면 **오서현(8개, FR 개수 최다)는 상담 상태머신·WebSocket·DataChannel이라는 응집된 실시간 도메인이라 외부 데이터로 대체할 수 있는 부분이 없고, 별도의 경감 요인도 없다.**

**결론**: 지금 이 시점에 FR을 강제로 재배분할 필요는 없다 — B의 8개 FR은 도메인 응집도가 높아 인위적으로 쪼개면 오히려 유지보수성이 떨어진다. 다만 팀은 **B가 실질적으로 가장 부담이 큰 축이 될 가능성이 있다는 것을 인지하고**, 아래를 1주차 회의에서 확인한다.

- [ ] A의 외부 공공데이터 확보 여부 확인 (확보 시 여유 시간을 B 지원으로 돌릴지 논의)
- [ ] 2주차 중간 체크포인트에서 B의 실제 진행 속도를 A/C와 비교 확인
- [ ] 필요 시 최주연(PM)이 FR-C-001~004 중 일부 지원 비중을 높이는 안을 사전 합의

## 13.4 검토했으나 기각한 안: 관리자 로그인(FR-A-001)의 신재령 이동

13.3절의 B 부담 완화 방안으로, 관리자 로그인(FR-A-001)만 신재령로 옮기는 안을 검토했다. 관리자 CRUD API(FR-A-002~005)를 이미 A가 전부 소유하고 있어 "관리자축은 A, 상담자축은 B"로 도메인이 깔끔하게 갈리고, FR 개수도 8/7로 역전되어 13.3절 문제를 완화한다는 논리였다.

**기각 사유**: 관리자 로그인과 상담자 로그인은 사용자 관점에서는 다른 화면·흐름이지만, 백엔드 구현에서는 Account 엔티티·Role·JWT 발급/검증·SecurityConfig를 공유하는 **단일 인증 모듈**이다. 이 공유 기반을 담당자별로 쪼개면:

- 인증 관련 코드(SecurityFilterChain, TokenProvider 등)가 두 곳에서 중복 또는 충돌 위험이 생긴다.
- FR 라벨은 둘로 나뉘어도 실제 작업량 대부분은 공유 기반 구축에 있으므로, 어느 한쪽이 먼저 만들면 다른 쪽은 사실상 얇은 컨트롤러만 얹는 정도로 끝나 "최종 책임자 분리"가 실질적 의미를 잃는다.
- 상담자 로그인은 상담자 계정 관리(FR-A-006)·상담 요청 목록(FR-C-002, 담당 역·상담 가능 상태 기준 필터링)과 강하게 엮여 있어, 로그인만 떼어내면 팀 간 불필요한 의존성이 생긴다.

**최종 결정**: 관리자 로그인(FR-A-001)은 원안대로 오서현가 유지한다. v3 당시 FR 소유권은 A 7개 / B 8개 / C 4개로 되돌렸다. B의 실질 부담 문제는 FR 재배분이 아니라 13.3절의 체크포인트 모니터링 방식으로 대응한다.


## 13.5 v4 역할 경계 보완: 최주연·김은지·신재령

`FR-U-008 출구 자동 추천`은 화면보다 공간 데이터와 경로 계산 의존성이 크므로 신재령으로 최종 책임을 변경했다. 이에 따라 최주연은 6개, 신재령은 8개의 FR을 최종 책임진다.

김은지는 FR 개수는 4개지만 카메라·지도·경로·WebRTC·DataChannel 등 기술 난도가 높은 화면을 맡는다. 상담자 로그인·요청 목록·요청 상세·수락·거절과 같은 일반 화면까지 모두 맡기면 실제 프론트 부담이 과도해지므로 최주연이 해당 화면을 구현한다.

역할 경계는 다음과 같이 운영한다.

- 최주연: PM·UX·사용자 보조 화면·상담자 일반 화면·다국어·정적 교통카드 추천
- 김은지: 카메라·권한·지도·경로·사용자 WebRTC·상담자 실시간 통화·DataChannel
- 신재령: 목적지 검색 API·출구 추천 계산·지도·시설·경로·좌표 앵커링
- 오서현: 상담 요청 생성부터 대기·수락·종료까지의 상태와 실시간 이벤트
