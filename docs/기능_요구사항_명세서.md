# 외국인 관광객 대상 지하철 실내 내비게이션 기능 요구사항 명세서

## 1. 문서 목적

본 문서는 외국인 관광객 대상 지하철 실내 내비게이션 서비스의 기능 요구사항을 정의한다.

기능 요구사항은 팀원이 같은 범위와 같은 완료 기준을 기준으로 개발할 수 있도록 작성한다.

본 문서는 관련 설계와 개발의 기준 문서로 사용한다.

- 프론트엔드 개발
- 백엔드 API 설계
- VPS 처리 설계
- WebRTC 상담 설계
- ERD 작성
- 테스트 케이스 작성
- 프로젝트 일정 및 역할 분담

---

## 2. 서비스 범위

### 2.1 MVP 범위

MVP는 역삼역을 대상으로 한다.

역삼역 외 다중 역사 확장은 8월 9일 이후 백로그로 관리한다.

MVP의 핵심 흐름은 다음과 같다.

```text
웹앱 접속
→ 언어 선택
→ 권한 요청
→ 현재 역 확인
→ 현재 위치 인식
→ 목적지 검색
→ 출구 추천
→ 실내 경로 안내
→ 출구 도착 확인
→ 외부 지도 앱 연계
→ 문제 발생 시 WebRTC 상담
```

### 2.2 우선순위 기준

| 우선순위 | 의미 |
| --- | --- |
| 필수 | MVP 시연과 핵심 사용자 흐름에 반드시 필요한 기능 |
| 중요 | MVP 품질을 높이지만 일부 제한 구현이 가능한 기능 |
| 도전 | 시간이 허용될 경우 구현하는 확장 기능 |
| 후순위 | MVP 이후 구현하는 기능 |

`PinGo_역할분배_최종기획안_v4.md` 기준으로 본 문서의 기능 요구사항 32개는 모두 필수 범위다. 기능 요구사항에 없는 신규 기능만 도전 또는 후순위 백로그로 분류한다.

### 2.3 최종 책임 기준

기능별 최종 책임자는 `PinGo_역할분배_최종기획안_v4.md`를 따른다.

| 담당 | 최종 책임 범위 |
| --- | --- |
| 최주연 | PM·UX·Frontend B, 사용자 보조 화면, 상담자 일반 화면, 교통카드 간단 추천 |
| 강민수 | AI 모델·VPS 데이터·보조 위치 인식 성능 검증 |
| 김은지 | Frontend A, 카메라·지도·경로·사용자 WebRTC·상담자 실시간 화면 |
| 신재령 | Backend A, 공간 데이터·경로 탐색·출구 추천·AI 결과 좌표 앵커링 |
| 오서현 | Backend B, 인증·상담 상태·WebRTC signaling·DataChannel |
| 이정우 | Backend C, 위치추정 AI Adapter·실패 판정·외부 연계·인프라 |

## 4. 기능 요구사항 목록

## 4.1 사용자 웹앱

### FR-U-001. 언어 선택

| 항목 | 내용 |
| --- | --- |
| 설명 | 사용자는 웹앱 최초 접속 시 서비스 언어를 선택할 수 있어야 한다. |
| 우선순위 | 필수 |
| 관련 화면 | U-01 언어 선택 화면 |

#### 세부 요구사항

- 시스템은 최초 접속 시 언어 선택 화면을 표시해야 한다.
- 사용자는 한국어 또는 영어를 선택할 수 있어야 한다.
- 선택한 언어는 이후 화면 문구에 반영되어야 한다.
- 일본어와 중국어는 MVP 이후 확장 대상으로 둔다.

#### 완료 기준

- 한국어와 영어 중 하나를 선택할 수 있다.
- 선택한 언어 값이 서비스 이용 중 유지된다.
- 언어 선택 후 권한 요청 화면으로 이동한다.

---

### FR-U-002. 초기 권한 요청

| 항목 | 내용 |
| --- | --- |
| 설명 | 시스템은 초기 진입 직후 위치정보, 카메라, 마이크 권한을 요청해야 한다. |
| 우선순위 | 필수 |
| 관련 화면 | U-02 권한 요청 화면 |

#### 세부 요구사항

- 시스템은 위치정보 권한을 요청해야 한다.
- 시스템은 카메라 권한을 요청해야 한다.
- 시스템은 마이크 권한을 요청해야 한다.
- 각 권한이 필요한 이유를 사용자에게 설명해야 한다.
- 사용자가 권한을 거부해도 제한 모드로 서비스를 계속 이용할 수 있어야 한다.

#### 완료 기준

- 권한 허용 버튼을 누르면 브라우저 권한 요청이 실행된다.
- 권한 허용 또는 거부 상태가 저장된다.
- 위치 권한 거부 시 역 직접 선택 흐름으로 이동한다.
- 카메라 권한 거부 시 지도 수동 위치 선택 흐름을 제공한다.

---

### FR-U-003. 현재 역 확인

| 항목 | 내용 |
| --- | --- |
| 설명 | 사용자는 GPS 기반 후보 또는 직접 검색으로 현재 역을 확정할 수 있어야 한다. |
| 우선순위 | 필수 |
| 관련 화면 | U-03 현재 역 확인 화면 |

#### 세부 요구사항

- 시스템은 GPS 기반으로 주변 지하철역 후보를 표시해야 한다.
- 사용자는 후보 역 중 하나를 선택할 수 있어야 한다.
- 사용자는 역 이름을 직접 검색할 수 있어야 한다.
- 위치 권한이 없을 경우 직접 검색과 선택을 기본으로 제공해야 한다.

#### 완료 기준

- 주변 역 후보가 표시된다.
- 사용자가 현재 역을 선택하면 `selectedStation`이 설정된다.
- 선택된 역 기준으로 지도, 시설, 경로 데이터가 로드된다.

---

### FR-U-004. 현재 위치 인식

| 항목 | 내용 |
| --- | --- |
| 설명 | 사용자는 카메라 기반 VPS 또는 보조 인식으로 역 내부 현재 위치를 확인할 수 있어야 한다. |
| 우선순위 | 필수 |
| 관련 화면 | U-04 현재 위치 인식 화면 |

#### 세부 요구사항

- 시스템은 현재 위치 인식 화면에서 카메라를 실행해야 한다.
- 사용자는 주변을 카메라로 비추고 위치 인식을 요청할 수 있어야 한다.
- 시스템은 VPS 또는 보조 위치 인식으로 위치 후보를 반환해야 한다.
- 시스템은 위치 인식 신뢰도를 표시해야 한다.
- 사용자는 위치 후보를 확인하고 선택할 수 있어야 한다.
- 위치가 확정되면 시스템은 그 시점을 상대 위치 추적의 앵커로 설정해야 한다. 상대 위치 추적은 FR-U-010에서 정의한다.

#### 완료 기준

- 카메라 화면이 정상 표시된다.
- 위치 인식 요청을 보낼 수 있다.
- 위치 후보와 신뢰도가 표시된다.
- 위치가 확정되면 `currentIndoorLocation`이 설정된다.
- 위치 확정 시점의 좌표와 방향이 상대 위치 추적 앵커로 전달된다.

### FR-U-005. 위치 인식 실패 대응

| 항목 | 내용 |
| --- | --- |
| 설명 | VPS 위치 인식이 실패해도 사용자가 대체 방식으로 현재 위치를 지정할 수 있어야 한다. |
| 우선순위 | 필수 |
| 관련 화면 | U-05 위치 인식 실패 화면, U-06 지도 수동 위치 선택 화면 |

#### 세부 요구사항

- 시스템은 VPS 실패 또는 낮은 신뢰도 상태를 사용자에게 알려야 한다.
- 사용자는 다시 촬영을 시도할 수 있어야 한다.
- 사용자는 주변 랜드마크 후보를 선택할 수 있어야 한다.
- 사용자는 실내 지도에서 현재 위치를 직접 선택할 수 있어야 한다.
- 사용자는 상담 요청으로 전환할 수 있어야 한다.

#### 완료 기준

- VPS 실패 시 재촬영, 랜드마크 선택, 지도 수동 선택, 상담 요청 중 하나를 선택할 수 있다.
- 수동 선택한 위치를 기준으로 경로 탐색을 진행할 수 있다.

### FR-U-006. 실내 지도 표시

| 항목 | 내용 |
| --- | --- |
| 설명 | 시스템은 대상 역의 층별 실내 지도를 표시해야 한다. |
| 우선순위 | 필수 |
| 관련 화면 | U-06 지도 수동 위치 선택 화면, U-10 경로 안내 화면 |

#### 세부 요구사항

- 시스템은 대상 역의 층별 지도를 표시해야 한다.

- 지도에는 주요 시설과 출구가 표시되어야 한다.
- 지도에는 현재 위치, 목적지, 경로가 표시되어야 한다.

#### 완료 기준

- 1개 대상 역의 층별 지도가 표시된다.
- 현재 위치와 목적지가 지도 위에 표시된다.
- 경로 안내 중 지도에 경로 라인이 표시된다.

### FR-U-010. 경로 안내

| 항목 | 내용 |
| --- | --- |
| 설명 | 시스템은 사용자가 목적지까지 이동할 수 있도록 카메라와 지도를 함께 제공해야 한다. |
| 우선순위 | 필수 |
| 관련 화면 | U-10 경로 안내 화면 |

#### 세부 요구사항

- 경로 안내 화면은 상단 카메라, 하단 지도 구조로 제공해야 한다.
- 카메라는 경로 안내 중 계속 유지되어야 한다.
- 카메라 화면 위에는 진행 방향 화살표가 표시되어야 한다.
- 지도에는 현재 위치, 목적지, 경로가 표시되어야 한다.
- 시스템은 단계별 안내 문장을 제공해야 한다.
- 시스템은 남은 거리와 예상 시간을 표시해야 한다.
- 사용자는 경로 안내 중 현재 위치 재인식을 요청할 수 있어야 한다.
- 사용자는 경로 안내 중 상담을 요청할 수 있어야 한다.

#### 상대 위치 추적 세부 요구사항

- 시스템은 WebXR 기반 상대 위치 추적으로 경로 안내 중 현재 위치를 갱신해야 한다.
- 상대 위치는 FR-U-004에서 확정된 위치를 앵커로 삼아 지도 좌표계 미터 좌표로 변환해야 한다.
- 변환 규칙은 `역삼역_FE_좌표연동_스펙.md`의 WebXR 정렬 절을 따라야 한다.
- 시스템은 사용자의 이동과 회전에 따라 지도 위 현재 위치와 방향 표시를 갱신해야 한다.
- 시스템은 위치 재인식이 성공하면 추적 앵커를 갱신해 누적 오차를 초기화해야 한다.
- 시스템은 WebXR 미지원, 권한 거부, 세션 실패를 구분해 처리해야 한다.
- 위 조건에서는 추적 없이 위치 재인식과 지도 수동 위치 선택으로 경로 안내를 계속해야 하며, 실시간 추적을 사용할 수 없다는 상태를 사용자에게 표시해야 한다.
- 상대 위치의 백엔드 전송 계약은 후속 Task에서 확정한다. 이 문서는 클라이언트 내부 갱신까지를 필수 범위로 둔다.

#### 완료 기준

- 카메라와 지도가 한 화면에 함께 표시된다.
- 방향 화살표와 안내 문장이 표시된다.
- 현재 위치 재인식과 상담 요청이 가능하다.
- WebXR 지원 환경에서 사용자가 이동하면 지도 위 현재 위치가 갱신된다.
- 위치 재인식 성공 시 추적 앵커가 갱신된다.
- WebXR 미지원 환경에서도 경로 안내가 중단되지 않고 추적 미지원 상태가 표시된다.

## 8. 아직 의사결정이 필요한 사항

다음 항목만 추후 확정한다.

1. 역삼역 내 실제 시연 동선
2. 상대 위치 추적 앵커의 방위값 출처와 백엔드 전송 계약. 세부 항목은 `기술_의사결정_정리.md` 12장에 있다.

다음 항목은 확정된 기준으로 개발한다.

| 항목 | 확정 기준 |
| --- | --- |
| MVP 대상 역 | 역삼역 |
| 프론트엔드 | React + TypeScript + Vite |
| 백엔드 | Spring Boot + Spring Data JPA + MySQL |
| 지도 표현 방식 | 이미지 지도 + 좌표 오버레이 |
| 경로 탐색 | 백엔드 Dijkstra |
| 외부 지도 | 네이버지도 |
| WebRTC signaling | WebSocket |
| WebRTC STUN/TURN | 무료 STUN 우선, 연결 불안정 시 TURN 추가 |
| VPS 실패 1순위 대체 | 지도 수동 선택 |
| VPS 실패 2순위 대체 | 랜드마크 선택 |
| 상대 위치 추적 | WebXR `immersive-ar` 세션 기반 pose 추적 |
| 추적 미지원 시 대체 | 위치 재인식 + 지도 수동 위치 선택 |
| 상담자 계정 생성 | 관리자 수동 등록 |
| 관리자 API | MVP에서 전체 구현 |
| 배포 방식 | Nginx reverse proxy + HTTPS |
| HTTPS 인증서 | Let's Encrypt 기준 |
