# 기술 의사결정 정리

> 최신화: 2026-07-30

## 1. 문서 목적

본 문서는 외국인 관광객 대상 지하철 실내 내비게이션 서비스의 MVP 개발을 위해 확정한 기술 및 구현 방향을 정리한다.

대상 역은 역삼역으로 확정한다. 실제 시연 대표 동선은 촬영 가능 구간과 구현 난이도를 기준으로 구현 중 확정한다. 그 외 개발 방식은 본 문서를 기준으로 진행한다.

## 3. 프론트엔드 결정

### 3.1 기술 스택

프론트엔드는 **React + TypeScript + Vite**를 사용한다.

### 3.2 선택 이유

- 모바일 웹앱을 빠르게 구현하기 좋다.
- 카메라, 위치 권한, WebRTC, 지도 오버레이 구현 사례가 많다.
- TypeScript를 통해 API 응답 타입을 안정적으로 관리할 수 있다.
- Vite 기반 개발 서버가 빠르고 설정 부담이 적다.

### 3.3 구현 기준

- 모바일 세로 화면을 우선한다.
- UI 스타일링은 CSS Modules와 CSS Variables를 사용한다.
- 아이콘은 lucide-react를 사용한다.
- 경로 안내 화면은 상단 카메라, 하단 지도 구조를 유지한다.
- 지도는 이미지 위에 현재 위치, 목적지, 경로, 시설 아이콘을 오버레이한다.
- 상담 버튼은 주요 화면에서 플로팅 버튼 형태로 접근 가능하게 둔다.

### 3.4 패키지 매니저 및 CI 기준

- 프론트엔드 패키지 매니저는 npm을 사용한다.
- Node.js는 20 LTS를 기준으로 한다.
- lockfile은 `package-lock.json`을 커밋한다.
- CI에서는 `npm ci` 후 `npm run build`를 필수로 실행한다.
- `lint`, `test` 스크립트가 있으면 CI에서 함께 실행한다.

## 4. 백엔드 결정

### 4.1 기술 스택

백엔드는 **Spring Boot + Spring Data JPA + MySQL**을 사용한다.

### 4.2 선택 이유

- REST API, 관리자 API, 인증, DB 연동을 안정적으로 구현할 수 있다.
- SSAFY 팀 프로젝트에서 팀원들이 익숙할 가능성이 높다.
- JPA를 통해 ERD 기반 엔티티를 빠르게 구현할 수 있다.
- 추후 다중 역사 확장에도 적합하다.

### 4.3 구현 기준

- 사용자 API, 상담자 API, 관리자 API를 분리한다.
- 관리자 API는 MVP에서 전체 구현한다.
- 초기 데이터는 seed로 준비할 수 있지만, seed는 관리자 API를 대체하지 않는다.
- 경로 탐색은 백엔드에서 수행한다.

### 4.4 백엔드 역할 경계

백엔드 담당 경계는 `PinGo_역할분배_최종기획안_v4.md`를 기준으로 한다.

| 담당 | 책임 범위 |
| --- | --- |
| 신재령 | 공간 데이터, 지도·시설·경로, 출구 추천, AI 결과 좌표 앵커링 |
| 오서현 | 인증, 상담 상태, WebSocket signaling, DataChannel 이벤트 계약 |
| 이정우 | 위치추정 AI Adapter, AI 응답 검증·상태 판정, 외부 지도, 위치 공유, 배포·네트워크 |

신재령은 AI 모델이나 AI 서버를 직접 다루지 않는다. AI 서버 호출, 응답 검증, timeout, circuit breaker, 실패 상태 판정은 이정우가 책임진다. 신재령은 검증된 위치 결과를 지도 좌표계와 유효 노드로 변환하는 앵커링을 책임진다.

WebRTC는 오서현과 이정우가 분리해 책임진다. 오서현은 signaling 메시지, 상담 상태, 재연결 로직, DataChannel 이벤트 의미 처리를 책임진다. 이정우는 HTTPS/WSS, reverse proxy, STUN/TURN, NAT 환경 확인, 외부망 연결 로그 등 네트워크·배포 환경을 책임진다.

IMU, DeviceOrientation, 카메라 방향 보정, 실시간 화살표 보정은 프론트엔드 책임이다. 백엔드는 지속적인 센서 스트림을 처리하지 않는다.

## 5. 인증 결정

### 5.1 사용자 인증

일반 관광객 사용자는 로그인하지 않는다.

사용자 상태는 `userSessionId` 기반 임시 세션으로 관리한다.

### 5.2 상담자/관리자 인증

상담자와 관리자는 JWT Access Token 기반으로 인증한다.

| 항목 | 결정 |
| --- | --- |
| Access Token 만료 시간 | 6시간 |
| Refresh Token | MVP에서는 사용하지 않음 |
| 전달 방식 | `Authorization: Bearer {accessToken}` |
| 사용자 세션 만료 | 생성 기준 6시간 (활동으로 연장되지 않음) |
| 상담 세션 ID | UUID 또는 ULID 기반 문자열 |

### 5.3 선택 이유

- 상담자와 관리자는 시연 중 재로그인 부담이 적어야 한다.
- MVP에서는 로그인 사용자가 제한적이므로 Refresh Token 없이 단순하게 구현한다.
- 권한 분리는 상담자와 관리자 API 보호에 충분하다.

## 6. 지도 및 경로 탐색 결정

### 6.1 지도 표현 방식

지도는 **이미지 지도 + 좌표 오버레이** 방식으로 구현한다.

### 6.2 선택 이유

- MVP에서 가장 빠르게 구현할 수 있다.
- 실제 지도 파일 위에 시설 좌표, 경로 좌표를 표시하기 쉽다.
- SVG나 Canvas 기반 정교한 지도 에디터보다 초기 제작 부담이 낮다.

### 6.3 좌표 기준

좌표는 **캐노니컬 미터 프레임**으로 저장한다. 지도 이미지 픽셀이 아니다.

| 항목 | 값 |
| --- | --- |
| 단위 | meter |
| 원점 | 역삼역 B2↔B3 층간 엘리베이터 — B2 평면도 픽셀 `(622, 512)` → `(0, 0)` |
| +X 방향 | 6번 출구 방향(승강장 축). 평면도 이미지 기준 약 −21.28° |
| 축척 | 0.19 m/px (provisional, COLMAP sim3 정합 후 확정) |
| z | B1 = 5, B2 = 0, B3 = −5 (명목값, 실제 층고 미확정) |

원점을 층간 엘리베이터로 잡은 이유는 **여러 층에 같은 평면 위치로 존재하는 수직 구조물**이어서다. 층별 평면도를 서로 정렬하는 기준점이 되고, COLMAP 사진에서도 식별할 수 있어 sim3 제어점으로 쓸 수 있다.

> **원점 엘리베이터의 명칭 주의**: 이 엘리베이터는 V4 시드에서 `EVA`(엘리베이터 A)로, 재구축 데이터에서는 `엘리베이터 B`로 명명돼 있다. **좌표는 동일하고 A·B 라벨만 뒤바뀐 상태**이며, 재시드 시 현장 표기를 기준으로 통일한다. 좌표 프레임 자체는 바뀌지 않으므로 sim3 정합 결과는 유효하다.
>
> **B1 프레임은 미검증 추정값이다**: B1에는 이 엘리베이터가 없어 원점 픽셀 `(594, 501)`을 평면도에 추정으로 얹었다. 층별 평면도가 같은 역 윤곽을 공유하므로 이미지 정합으로 검증할 수 있는데, 예비 측정에서 현재 값과 최대 4.4m 차이가 나왔다(방법 오차 ±2m). B1 내부 좌표는 자기일관적이라 B1 단독 라우팅·렌더링에는 영향이 없고, **층 전환 시 위치 정합에만 영향이 있다.** COLMAP 제어점에 B1을 포함해 sim3 잔차로 확정한다.

- 시설·노드·경로 좌표는 `mapX`, `mapY`, `mapZ`에 미터로 저장한다.
- 실제 거리 계산은 `route_edge.distanceM` 값을 우선 사용하고, 값은 3D 유클리드(x, y, z)로 산출한다.
- 이미지 픽셀 ↔ 미터 변환에 필요한 원점 픽셀·회전각·축척은 층별 좌표 프레임으로 공유한다. 프레임 값과 변환식은 [`역삼역_route_node_naming.md`](역삼역_route_node_naming.md) §1, FE 연동 계약은 [`역삼역_FE_좌표연동_스펙.md`](역삼역_FE_좌표연동_스펙.md)를 기준으로 한다.

#### 픽셀이 아니라 미터인 이유

- **평면도가 교체되면 픽셀 좌표는 전부 무효가 된다.** 현재 평면도는 안내용 약도이고 실측 도면으로 교체할 여지가 있다. 미터 프레임은 이미지에 독립적이다.
- **회전을 픽셀로 표현할 수 없다.** 평면도가 약 −21.28° 기울어져 있고 미터 프레임은 +X를 승강장 축에 맞춘다. 픽셀 좌표계에서는 "복도 따라 5m"가 x·y 혼합이 된다.
- **`map_z`(층 높이)는 미터다.** x·y만 픽셀이면 같은 행에 단위가 섞인다.
- **`route_edge.distance_m`이 경로 탐색 가중치다.** 픽셀 거리로는 층간 이동과 수평 이동을 같은 단위로 다룰 수 없다.
- **FR-U-011의 출구 근접 판정이 미터 임계값이다.** 픽셀이면 평면도가 바뀔 때마다 임계값이 달라진다.
- **COLMAP↔평면도 sim3 정합(S15P11A206-277)이 미터를 목표로 피팅돼 있다.**

**대안 검토**: 픽셀로 통일 → 위 사유로 불가. 픽셀·미터 동시 저장 → 이중 관리로 어긋날 위험이 있어 채택하지 않는다.

**영향 범위**: FE는 좌표 프레임으로 미터→픽셀을 변환한다(구현됨). AI/VPS는 영향이 없다 — COLMAP 좌표를 그대로 반환하고 변환은 백엔드가 수행하며, 캐노니컬 프레임이 유지되는 동안 응답 계약은 불변이다.

### 6.4 경로 탐색 방식

경로 탐색은 백엔드에서 수행한다.

MVP에서는 **Dijkstra 알고리즘**을 우선 사용한다.

### 6.5 경로 옵션 처리

MVP에서는 다음 2가지 경로 옵션을 제공한다.

| 화면 표시명 | 내부 routeType | 처리 기준 |
| --- | --- | --- |
| 빠른 경로 | `fastest` | 모든 active edge를 허용하고 `distanceM` 기준으로 가장 짧은 경로를 찾는다 |
| 엘리베이터 이용 경로 | `elevator_only` | `moveType = stair`, `moveType = escalator` 간선을 제외한다 |

엘리베이터 이용 경로는 엘리베이터 간선만 쓰는 경로가 아니라, 평지 통로와 엘리베이터를 함께 사용해 **계단·에스컬레이터 없이 도달 가능한** 경로를 의미한다.

기획 원안은 3종(빠른 / 계단 없는 / 엘리베이터 중심)이었으나, `계단 없는`과 `엘리베이터 중심`은 실제 처리 기준이 같아져 `elevator_only` 1종으로 통합했다. 현재 API가 제공하는 경로 타입은 `fastest`, `elevator_only` 두 가지이며, 그 외 값은 `UNSUPPORTED_ROUTE_TYPE`으로 거부된다.

가중치는 `distanceM`이다. `estimatedTimeSec`은 일부 간선에서 비어 있어 MVP에서는 정렬 기준으로 쓰지 않고 표시용으로만 사용한다.

## 7. VPS 실패 대응 결정

### 7.1 자체 VPS

스마트폰 촬영 영상에서 프레임 이미지를 추출하고, COLMAP 기반 3D Map 구축을 우선 시도한다.

### 7.2 실패 대응 우선순위

| 순위 | 방식 | 설명 |
| --- | --- | --- |
| 1 | 지도 수동 선택 | 사용자가 실내 지도에서 현재 위치를 직접 선택 |
| 2 | 랜드마크 선택 | 사용자가 주변 시설 또는 안내판 후보를 선택 |
| 3 | QR/마커 | 시연 안정성을 위한 백업 수단 |
| 4 | WebRTC 상담 | 사용자가 직접 해결하지 못할 경우 상담 연결 |

### 7.3 이미지 처리 원칙

- 카메라 이미지는 위치 인식 처리 후 즉시 폐기한다.
- 실패 분석을 위해 저장해야 할 경우 별도 동의를 받는다.
- MVP 기본 정책은 저장하지 않는 것이다.

## 8. 외부 지도 연계 결정

### 8.1 우선 연계 대상

외부 지도 앱 연계는 **Kakao Map**을 적용한다.

### 8.2 연계 방식

- 웹 링크를 우선 사용한다.
- Kakao Map 앱 링크를 우선하고 앱 실행이 불가능하면 웹 링크로 대체한다.
- 앱 실행 실패 시 웹 링크로 대체한다.
- 웹 링크도 실패할 경우 장소명 또는 주소 복사 기능을 제공한다.

### 8.3 출발지/도착지 기준

| 항목 | 기준 |
| --- | --- |
| 출발지 | 사용자의 실제 현재 GPS 위치 |
| 도착지 | 사용자가 우리 서비스에서 선택한 외부 목적지 |
| 이동 방식 | 도보 |

사용자가 실내 안내와 다른 출구로 나간 경우에도 실제 현재 위치를 출발지로 사용해 외부 길찾기를 이어간다.

## 9. WebRTC 결정

### 9.1 Signaling

WebRTC signaling은 **WebSocket**으로 구현한다.

### 9.2 STUN/TURN

## 11. WebXR 상대 위치 추적 결정

### 11.1 채택 범위

경로 안내 중 사용자의 **상대 위치 추적**은 WebXR `immersive-ar` 세션으로 구현한다.

VPS(`POST /api/vps/localize`)는 **절대 위치를 확정**하는 수단이고, WebXR은 **확정된 위치 사이의 이동을 이어주는** 수단이다. 두 방식은 대체 관계가 아니라 보완 관계다.

실제 공간에 3D 오브젝트를 고정 렌더링하는 AR과 ARCore·ARKit 네이티브 전환은 계속 후순위·제외 범위다. WebXR 세션은 pose 수집 목적으로만 사용하며 MVP에서 3D 렌더링은 하지 않는다.

지원 환경 검증 기록과 실기기 체크리스트는 `WebXR_검증_결과.md`에 있다. 2026-07-30 1·2차 실기기 검증으로 세션·pose 수집·좌표 방향·층 전환 감지·카메라 자원 조건이 모두 확인돼 S15P11A206-295 이후 구현에 착수할 수 있다. 남은 미확인 항목은 13장에 있으며 착수를 막는 항목은 없다.

### 11.2 좌표계 정렬 기준

WebXR reference space의 원점과 방향은 **세션을 시작한 순간의 단말 위치·방향**이므로 역 좌표계와 회전 오프셋이 존재한다. 정렬은 다음 기준을 따른다.

- 위치 확정(VPS 인식 성공 또는 수동 선택) 시점의 지도 미터 좌표와 그 순간의 XR pose를 **한 쌍의 앵커**로 저장한다.
- 앵커 시점의 전방 벡터 두 개(XR 평면·지도 평면)로 회전을 산출하고, 이후 XR 상대 이동량에 이 회전을 적용해 지도 미터 좌표로 변환한다. 각도 뺄셈을 쓰지 않는 이유는 0도 기준과 회전 방향 규약을 별도로 합의해야 하기 때문이다.
- 위치 재인식이 성공하면 앵커를 갱신해 누적 오차를 초기화한다.
- 나침반(`deviceorientation`)은 보조 지표로만 사용한다. 앵커 기준 상대 정렬이므로 `northBearing` 확정에 의존하지 않는다.
- 변환식과 층 처리 규칙은 `역삼역_FE_좌표연동_스펙.md` 8장에 둔다.
- XR 높이(`Y`)의 **절대값으로 층을 계산하지 않는다.** `local` reference space의 원점 높이는 세션을 시작한 순간 단말이 들려 있던 높이여서 알 수 없고, 프레임의 층별 `z`도 명목값이다.
- XR 높이의 **변화량(ΔY)은 층 전환 감지에 사용한다.** 원점 높이를 몰라도 상승·하강은 판정된다.
- `floorId` 확정 근거는 위치 재인식, 수동 선택, 경로 단계 진행이다. ΔY는 단독 확정 근거가 아니라 경로 단계와 결합해 "예상된 층 전환이 실제로 일어났는지" 확인하는 신호다.

**엘리베이터·에스컬레이터 구간에서는 ΔY를 쓰지 않는다.** 3차 실기기 검증에서 엘리베이터 2개 층 상승 시 pose 결손률이 19.5%(평지 1.7%), 최장 7초 연속 결손이었고, ΔY가 `1.03 → 0.12 → 4.06 → 2.82`로 오르내리며 내린 뒤에도 `2.81` ~ `3.04m`에서 안정되지 않아 실제 상승의 절반 이하에 그쳤다(층고를 보수적으로 3.0m로만 잡아도 2개 층 6.0m 대비 절반 수준이다). **결손 사이에 반환된 pose도 값이 틀렸으므로** "pose가 있으면 신뢰한다"는 규칙으로는 걸러지지 않는다. 경로의 `moveType`이 `elevator`인 구간에서는 ΔY를 판정에 넣지 않고, 통과 후 위치 재인식으로 층을 확정한다. 에스컬레이터는 미검증이나 같은 이유(시각 특징 부족·충돌)가 예상되므로 동일하게 처리하고, 실측 후 해제 여부를 정한다.

**ΔY 임계값은 층고가 아니라 잡음 바닥을 기준으로 잡는다.** 역삼역은 계단마다 높이가 달라 특정 층고를 기준으로 삼을 수 없다. 2차 실기기 실측에서 평지 28m 보행 중 ΔY는 `-0.13` ~ `+0.07`에 머물렀고, 정지 상태 지터는 0.01~0.03m였다. 한 층을 오르내린 뒤 원위치 복귀 시 ΔY는 `0.135`로 돌아와 상승·하강이 상쇄됐다. 잡음이 `±0.15m` 수준이므로 1m 안팎의 낮은 임계값을 써도 오탐이 발생하지 않으며, 가장 낮은 계단에서도 전환을 놓치지 않는다. 임계값의 최종값은 역삼역 실측 후 확정한다.

**앵커 시점 방향(`forwardMap`)의 출처는 2026-07-31 AI·BE 협의로 확정됐다.** 위치 인식 응답에 방향 필드를 추가한다. 좌표계는 **캐노니컬**(같은 응답의 `mapX`/`mapY`와 동일 프레임)이고 형태는 **수평면 2D 단위벡터**다. 각도가 아니라 벡터로 받는다 — 각도는 0도 기준과 회전 방향 규약을 따로 합의해야 하고 좌표 스펙 이전 판이 그 문제로 폐기됐다. AI 파이프라인 설계서 8.1~8.2에 산출 방법이 이미 정의돼 있어 새로 계산하는 것이 아니라 기존 값을 응답에 노출하는 것이다. 필드명·정규화 주체·`null` 허용 여부는 통합 때 확정한다. 세부는 `역삼역_FE_좌표연동_스펙.md` 8.5에 있다.

> 협의 당시 전제였던 `candidates[]` 배열은 S15P11A206-128 에서 없어졌다. 위치는 좌표 한 점(`position`)으로 내려가므로 방향 필드도 **후보별이 아니라 단일 필드**가 된다. 노드는 경로 탐색 진입점(`startNodeId`)으로만 쓴다.

**앵커는 사전 위치 확정으로 만들지 않는다.** 초기 위치 인식(U-05)과 지도 수동 선택(U-07)은 경로 안내 화면보다 앞이고, 그 시점에는 XR 세션이 없어 짝지을 pose가 없다(11.7의 세션 개시 시점, 11.8의 카메라 자원 분리). 사전 확정 좌표는 표시용으로만 쓰고, 앵커는 경로 안내 화면에서 세션이 추적을 잡은 뒤 세션 안에서 VPS를 수행해 만든다. `camera-access`로 프레임을 꺼내므로 세션을 끊지 않는다(11.8). 따라서 사전 확정이 VPS였는지 수동 선택이었는지는 앵커에 영향을 주지 않는다.

**미결**: 위 세션 안 VPS를 사용자 조작 없이 자동 1회로 돌릴지, 재인식 버튼을 눌러야 수행할지 정하지 않았다. 함께 정해야 할 항목으로 `화면_정의서.md` U-10의 "현재 위치 다시 인식" 처리가 "U-04 화면 또는 인식 모듈 실행"으로 열려 있다. 화면을 벗어나면 세션이 끊겨 앵커가 사라지므로 같은 화면 안에서 수행하는 쪽이어야 하며, 안내 중 재인식이 쓸 엔드포인트(`POST /navigation/relocalize`)도 `API_명세서.md`에 아직 없다.

### 11.3 책임 경계

- 프론트엔드가 앵커와 XR 상대 이동량을 합산해 **지도 미터 좌표 `{x, y, floorId}`**를 산출한다.
- 미터 좌표를 route node에 매핑하는 작업은 기존 경계대로 백엔드가 수행한다.
- Python 위치추정 서비스는 WebXR 추적에 관여하지 않는다. `Python_HLOC_구현_계획.md`의 제외 항목과 일치한다.

### 11.4 샘플 확정 주기

XR frame은 표시 주기로 들어오므로(실측 약 30fps) 프론트엔드에서 다음 기준으로 추려 위치를 확정한다.

| 항목 | 기준 |
| --- | --- |
| 갱신 조건 | 직전 확정 위치 대비 **0.25m 이상 이동** |
| 최소 간격 | 100ms |
| 변화 없을 때 | 5초마다 1회 확정 |
| 중단 조건 | 경로 안내 화면을 벗어나면 세션과 추적을 중단한다 |

**회전은 확정 트리거에서 제외한다.** 초안은 `15° 이상 회전`을 포함했으나 1차 실기기 실측에서 이 조건이 상시 참이 되었다. 손에 들고 걸으면 단말 yaw가 자연스럽게 흔들려 회전량 중앙값이 23.5°였고, 그 결과 확정 38회 중 30회가 회전으로 발화하고 63%가 최소 간격에 걸려 나갔다. 의도한 거리 기준은 6회만 작동해 규칙이 사실상 "1초마다 갱신"으로 퇴화했다.

**거리·간격 기준을 `2m·1초`에서 좁혔다 (S15P11A206-79).** 그 값은 2차 실측에서 규칙 자체로는 적합했다 — 보행 중 확정 간격이 1297~1861ms였고 최소 간격에 한 번도 걸리지 않았으며, 정지 상태에서는 5초 heartbeat만 동작했다. 그러나 안내 화면 지도에 시점 추종이 붙으면서(FR-U-006) 그 간격이 화면에서 드러났다. 지도가 1.3~1.9초에 한 번씩 끊어 움직여 실시간으로 보이지 않는다. `0.25m·100ms`는 초속 1.2m 보행에서 약 5Hz다. 최소 간격은 빨리 걸을 때 확정이 프레임마다 나가지 않게 막는 상한으로만 남는다.

이 값을 다시 손볼 때는 **표시 데드밴드를 함께 본다.** `displaySmoothing.ts`의 데드밴드가 갱신 거리보다 크면 확정이 아무리 자주 와도 마커가 한 번도 움직이지 않는다. 두 값은 따로 정할 수 없다.

퇴화 사례는 회전 조건에서 온 것이므로 거리·간격을 좁히는 것과 무관하다. **회전을 확정 트리거로 되돌리지 않는다는 결정은 그대로다.**

**상태 확정과 화면 표시를 분리한다.** 회전량은 계속 관측하지만 확정·전송 단위를 만들지 않는다. 지도 위 방향 표시는 위치 확정과 **별도 채널**로 갱신한다.

| 항목 | 기준 | 근거 |
| --- | --- | --- |
| 갱신 조건 | 직전 표시 방향 대비 **5° 이상 회전** | 손에 든 단말의 흔들림을 걸러야 하지만 실측에 평면 yaw 지터 값이 없다. 확정 트리거에서 상시 참이던 15°(1초 창)보다 훨씬 작게 두어 의도한 회전이 곧 반영되게 한다 |
| 최소 간격 | 120ms | 30fps에서 프레임 3~4개당 한 번. 매 프레임 갱신은 위 표가 제거한 것이므로 상한을 둔다 |

두 값은 **provisional이며 13장 검증 항목이다.** 구현은 `frontend/src/shared/lib/webxr/session.ts`의 `PROVISIONAL_HEADING_DEADBAND_DEG`·`PROVISIONAL_HEADING_MIN_INTERVAL_MS`이며, 컨트롤러의 `subscribeHeading`이 각도만 흘린다. 회전을 위치 확정 트리거로 되돌리면 위 표가 제거한 퇴화가 그대로 돌아오므로 **채널을 합치지 않는다.**

**방향각에는 평활을 걸지 않는다.** 표시 평활은 위치의 데드밴드·추종 비율로 정의돼 있고(11.2, S15P11A206-296) 각도에 그 규칙을 그대로 쓸 수 없다 — 179°와 -179°가 이웃이라 선형 보간이 한 바퀴 돌아간다. 각도의 떨림은 위 데드밴드가 담당한다.

위치 스냅샷 주기로 방향을 갱신하면 **제자리에서 몸만 돌렸을 때 5초 heartbeat까지 늦는다.** S15P11A206-141의 실기기 확인에서 이 지연이 드러나 별도 채널로 분리했다.

**세션 시작 직후 0.96~1.54초 동안은 pose가 없다.** `requestReferenceSpace`가 성공한 뒤에도 ARCore가 추적을 잡을 때까지 `getViewerPose`가 `null`을 반환한다. 이 구간에는 확정 위치를 만들지 말고 직전 VPS 절대 좌표를 그대로 표시한다.

백엔드 전송 조건을 정할 때는 이 주기를 승계한다.

### 11.5 속도·가속도

- pose 위치의 시간 차분으로 프론트엔드가 속도와 가속도를 계산한다. `devicemotion` 센서를 사용하지 않으므로 추가 권한이 필요하지 않고 FR-U-002 권한 목록도 변경되지 않는다.
- **미정**: 속도·가속도의 사용 목적(정지·보행 상태 구분, pose 신뢰도 판정, 경로 이탈 감지 중 무엇인지)과 백엔드 전송·저장 여부. 목적이 확정되기 전까지 클라이언트 내부 값으로만 사용한다.

### 11.6 백엔드 전송 계약

이번 범위에서 확정하지 않는다. 클라이언트 내부 위치 갱신까지를 필수 범위로 두고, 전송 계약은 후속 Task에서 확정한다.

후속 Task에서 정해야 할 항목은 다음과 같다.

1. 전송 방식: 기존 `PATCH /user-sessions/{userSessionId}` 필드 확장 또는 신규 엔드포인트 신설
2. 요청 필드: `{x, y, floorId}` 외에 원시 pose·속도·가속도 포함 여부
3. 고빈도 호출이 `user_session`의 `last_active_at`·`expires_at` 연장에 미치는 영향
4. 연속 위치 샘플의 저장 여부와 저장 시 ERD 반영 (현재 `user_session.current_node_id`와 `localization_log`만 존재)

`API_명세서.md`와 `erd_최종.md`는 위 항목이 확정된 뒤 수정한다.

### 11.7 미지원 환경 대응

모든 조건에서 경로 안내 자체는 막지 않는다. 추적 없이 위치 재인식과 지도 수동 위치 선택으로 안내를 유지하고, 실시간 추적을 쓸 수 없다는 상태를 화면에 표시한다. iOS Safari는 `immersive-ar`을 지원하지 않으므로 이 경로가 기본 동작이 된다.

**조건 판별은 오류 `name`으로 하지 않는다.** 1차 실기기 검증에서 권한 거부가 `NotAllowedError`가 아니라 `NotSupportedError`로 나타났다. 오류 이름이 원인을 지시하지 않으므로, 판별은 `isSessionSupported` 결과와 `requestSession` 실패까지 걸린 시간으로 한다.

| 조건 | 판별 | 사용자 안내 |
| --- | --- | --- |
| `navigator.xr` 없음 | 객체 부재 | 이 브라우저에서는 실시간 추적을 쓸 수 없음 |
| `immersive-ar` 미지원 | `isSessionSupported` = `false` | 이 기기에서는 쓸 수 없음. **재시도 안내를 하지 않는다** |
| 권한이 이미 차단됨 | `isSessionSupported` = `true`이고 실패까지 **500ms 미만** | **브라우저 사이트 설정에서 권한을 초기화해야 함.** 앱 안에서는 복구할 수 없다 |
| 이번 요청 거부·일시적 실패 | `isSessionSupported` = `true`이고 실패까지 500ms 이상 | 재시도 가능 |
| 세션 중단 | `end` 이벤트 | 재시작은 사용자 조작으로만 수행 |
| 추적 상실 | `getViewerPose`가 연속 `null` | 위치 갱신을 멈추고 "위치 확인 중"을 표시. 복구되면 자동 재개 |
| 엘리베이터·에스컬레이터 통과 | 경로 `moveType` | 구간 내 추적을 신뢰하지 않는다. 통과 후 재인식 유도 |

추적 상실은 pose 부재로 드러나므로 감지할 수 있다. 실측에서 엘리베이터 상승 중 7초간 pose가 없었고, 그동안 위치 확정이 아예 발화하지 않아(`afterMs: 8746`) 갱신이 자연히 멈췄다. 화면이 얼어붙은 것처럼 보이지 않도록 상태 표시가 필요하다.

실측값은 차단 상태 10ms, 프롬프트가 뜬 경우 2.0~25.3초였다. 임계값 500ms는 그 사이에서 잡았다. 표본이 적어 **보조 신호로 쓰고 단독 판단 근거로 삼지 않는다.**

**권한 거부는 앱 내에서 되돌릴 수 없다.** 한 번 거부하면 이후 `requestSession`은 프롬프트 없이 즉시 실패한다. 실측한 기기에서는 브라우저 설정의 권한 초기화 경로를 찾지 못했고 시크릿 모드로도 복구되지 않았다(원인 미상). 거부한 사용자는 영구히 fallback 경로를 타므로, **추적 없이도 안내가 완결되어야 한다는 원칙을 우선한다.**

**AR 세션 동의는 카메라 권한으로 갈음되지 않는다.** 앱은 초기 진입 직후 위치·카메라·마이크를 일괄 요청하지만(`화면_흐름도.md` 5.2), 2차 실기기 검증에서 카메라가 허용된 상태에서도 세션 시작 시 별도 프롬프트가 떴다. 나아가 **AR 동의와 `camera-access` 동의도 서로 별개**여서, 권한을 초기화한 뒤 측정하면 프롬프트가 두 번 뜬다.

| 요청 | 조건 | 프롬프트 |
| --- | --- | --- |
| `["dom-overlay"]` | 권한 초기화 직후 | 뜸 |
| `["dom-overlay","camera-access"]` | 위 동의 10초 뒤, 같은 페이지 로드 | 또 뜸 |
| `["dom-overlay","camera-access"]` | 둘 다 허용 후 새로고침 | 뜨지 않음 |

**두 동의 모두 origin에 저장된다.** 새로고침 후에도 프롬프트가 없었으므로(185ms에 세션 시작) 사용자는 앱 최초 1회만 프롬프트 두 개를 연속으로 본다.

**세션 전 안내를 카메라 권한 요청처럼 쓰지 않는다 (S15P11A206-79).** 카메라는 5.2에서 위치·마이크와 함께 이미 받았다. 안내 문구가 권한을 처음 요청하는 것처럼 읽히면 사용자는 같은 것을 두 번 묻는다고 받아들인다. 이 안내가 정하는 것은 **그 카메라로 실시간 추적을 켤지** 하나다.

**프롬프트가 두 개 뜬다는 설명은 문구에 넣지 않는다.** 위 표대로 그 일은 앱 최초 1회에만 일어나고 그 뒤로는 프롬프트 자체가 없다. 대부분의 진입에서 일어나지 않는 일을 매번 설명하면 정작 물어보는 것이 묻히고, 실제로 뜨는 경우에는 시스템 대화상자가 스스로 무엇을 묻는지 알려준다.

실패 안내는 "카메라 권한"이 아니라 **"AR 사용 동의"**가 막혔다고 써야 한다. 카메라 권한은 허용돼 있으므로 초기 권한 화면을 다시 찾아가게 만들면 안 된다.

**동의 상태를 미리 조회할 수 없다.** `navigator.permissions.query({name: 'xr-spatial-tracking'})`는 Chrome 150에서 `TypeError`를 던진다. 상태에 따라 안내를 켜고 끌 수 없으므로 **세션 전 안내는 항상 표시한다.**

이 API를 호출하는 코드를 남긴다면 **`try`로 감싸고 Promise 거부도 함께 처리한다.** WebXR 관련 permission 이름은 벤더마다 구현이 달라 `xr-spatial-tracking` 외에 `xr`이나 `{ name: 'xr', mode: 'immersive-ar' }` 형태를 쓰는 구현도 있다. 인자 변환 단계에서 **동기 throw**가 날 수 있으므로 `.catch()`만으로는 잡히지 않으며, 초기화 경로에서 던지면 이후 코드가 통째로 실행되지 않는다. 조회 실패는 정상 분기로 취급하고 안내를 표시하는 쪽으로 넘어간다.

이에 따라 다음을 확정한다.

1. 경로 안내 진입 시 세션을 **자동으로 열지 않는다.** 먼저 앱 자체 안내를 표시하고, 사용자가 확인을 누르면 세션을 연다.
2. 안내 문구는 시스템 프롬프트가 **연속 두 번** 뜬다는 사실을 포함한다.
3. `camera-access`는 세션 시작 시 함께 요청한다. 세션 도중에 기능을 추가할 수 없어 두 프롬프트를 하나로 줄일 방법이 없다.

거부가 영구적이므로(위 문단) 사용자가 맥락을 이해한 뒤 프롬프트를 만나게 하는 것이 이 순서의 이유다. XR 동의는 `getUserMedia`처럼 조용히 미리 받는 API가 없어 세션을 실제로 여는 것 외에 방법이 없다.

### 11.8 카메라 자원 사용 규칙

**`getUserMedia`와 `immersive-ar` 세션은 공존하지 못한다.** 2차 실기기 검증에서 카메라 미리보기를 켠 채 세션을 열면 세션 시작·`XRWebGLLayer`·`requestReferenceSpace`·`dom-overlay`가 모두 성공하는데 `getViewerPose`만 전 프레임 `null`이었고 카메라 화면도 검은 상태였다. 카메라 트랙은 `readyState: live`로 남아 브라우저가 회수하지 않았다. **예외도 오류 이벤트도 없이 조용히 실패한다.**

이에 따라 다음을 규칙으로 한다.

- `requestSession` 호출 전에 모든 `getUserMedia` 카메라 트랙을 `stop()` 하고, 스트림을 물고 있던 `<video>`의 `srcObject`도 `null`로 되돌린다. `stop()`만으로는 일부 모바일 엔진에서 비디오 요소의 참조가 남아 카메라 자원이 완전히 반환되지 않을 수 있고, 그 경우 세션의 카메라 확보가 지연되거나 실패한다. 초기 권한 화면은 `stopMediaStream`으로 트랙을 정리한다.
- 미디어 스트림의 획득·해제를 화면마다 흩어 두지 않고 **전용 훅 또는 유틸리티로 모아 관리**한다. 경로 안내를 끝내고 수동 위치 선택 화면 등으로 돌아갈 때 `getUserMedia`를 다시 안정적으로 시작해야 하므로, 생명주기를 한 곳에서 책임지는 편이 누락을 막는다.
- 경로 안내 화면의 카메라 영상은 **XR 세션이 직접 그린다.** `<video>`로 띄우지 않는다. 지도와 안내 UI는 `dom-overlay`(`type: screen`)에 얹는다.
- 위치 재인식 화면처럼 세션 없이 카메라만 쓰는 화면은 `getUserMedia`를 그대로 쓴다. 화면을 벗어날 때 트랙을 정지한다.

**경로 안내 중 VPS 프레임은 `camera-access`로 확보한다.** 2차 검증에서 `enabledFeatures`에 `camera-access`가 부여됐고 `XRView.camera`(895×1920)와 `getCameraImage`가 성공했다. 세션을 유지한 채 프레임을 얻을 수 있으므로 재인식 때문에 세션을 끊고 앵커를 버릴 필요가 없다.

확인된 범위는 **GPU 텍스처 획득까지**다. 텍스처를 픽셀로 읽어 인코딩·전송하는 경로의 성능은 측정하지 않았으며, 13장 검증 항목으로 둔다.

**리드백은 동기 `readPixels`로 하지 않는다.** 동기 리드백은 GPU 파이프라인을 flush하며 메인 스레드를 막는다. `getCameraImage`가 준 텍스처는 895×1920이므로 RGBA 기준 약 6.9MB이고, 30fps 세션의 프레임 예산 33ms를 넘기기 쉽다. pose 추적 루프가 같은 스레드에서 도는 만큼 프레임 드롭으로 직결된다. 설계 방향은 다음과 같다.

| 항목 | 방침 |
| --- | --- |
| 리드백 방식 | WebGL2의 Pixel Buffer Object + `fenceSync`·`clientWaitSync`로 비동기 처리 |
| GL 컨텍스트 | **`webgl2`로 만든다.** PBO는 WebGL2 기능이다. 검증 페이지는 `webgl`(WebGL1)이라 이 경로를 시험할 수 없었다 |
| 텍스처 수명 | `getCameraImage`가 준 텍스처는 **해당 `XRFrame` 안에서만 유효**하다. 비동기로 읽으려면 프레임 안에서 자체 프레임버퍼로 복사한 뒤 그 대상에서 읽는다 |
| 해상도 | 리드백 전에 축소해 데이터량을 줄인다. 특징점 매칭은 원본 해상도를 요구하지 않는다 |
| 호출 주기 | VPS 요청을 수 초 단위로 제한해 리드백 빈도 자체를 낮춘다 |

비동기 경로를 쓰지 못하는 상황이면 호출 주기 제한만으로도 버틸 수 있는지 실측해 판단한다. 어느 쪽이든 **매 프레임 리드백은 하지 않는다.**

8. 11.4 샘플 확정 주기의 실측 적정값 — 개정 규칙(`2m·1초`)이 2차 실측에서 규칙으로는 적합했으나, 안내 지도 시점 추종에서 갱신이 끊겨 보여 `0.25m·100ms`로 좁혔다 (S15P11A206-79). 좁힌 값은 아직 실기기에서 재측정하지 않았다. **확인할 것은 둘이다** — 갱신이 잦아져 마커가 잡음을 따라 떨리는지, 그리고 확정 빈도가 pose 루프나 배터리에 영향을 주는지

12. 위치 인식 응답 방향 필드의 FE 통합 검증 (11.2, `역삼역_FE_좌표연동_스펙.md` 8.5). BE가 `candidates[]`에 방향 필드를 추가한 뒤 수행한다. **방향이 틀려도 오류가 나지 않고 마커만 엉뚱한 쪽으로 움직이므로** 8.5의 판정 기준(직선 복도 10m 직진)이 유일한 판별 수단이다. FE 수정 지점은 `frontend/src/features/xr-tracking/model/anchorForward.ts` 한 곳이며, 필드명 확정 후 후보 목록을 확정된 이름 하나로 줄이고 목업 상수와 `useMock` 스위치를 제거한다
13. 방향 표시 갱신 기준의 실기기 확정 (11.4, S15P11A206-141). `session.ts`의 데드밴드 `5°`와 최소 간격 `120ms`는 평면 yaw 지터가 측정되지 않은 상태에서 잡은 임시값이다. **정지 상태에서 부채꼴이 떨리면 데드밴드를 올리고, 몸을 돌렸을 때 따라오는 것이 늦으면 간격을 내린다.** 위치 확정 채널과 분리돼 있으므로 이 값을 바꿔도 위치 갱신 주기는 영향을 받지 않는다
14. 지도 마커 표시 평활 상수의 실기기 확정 (S15P11A206-296). `displaySmoothing.ts`의 데드밴드와 추종 비율은 2차 실측의 정지 지터 0.01~0.03m와 평지 ΔY 잡음 ±0.15m에서 유추한 임시값이다. 평면 지터는 따로 측정되지 않았다. 정지 상태에서 마커가 눈에 띄게 떨리는지(데드밴드가 낮음)와 보행 중 마커가 사용자보다 뒤처지는 게 체감되는지(추종 비율이 낮음)를 확인한다. 초안 `0.3m·0.6`은 안내 지도 검증에서 지연이 체감돼 `0.08m·0.9`로 바꿨다 (S15P11A206-79). **데드밴드는 8번의 갱신 거리보다 작아야 한다** — 크면 확정이 아무리 자주 와도 마커가 움직이지 않는다
15. 걸음 흔들림에 대한 지도 회전 문턱의 실기기 확정 (S15P11A206-79). `useSmoothedRotation.ts`의 `PROVISIONAL_ROTATION_HOLD_DEG` 12°는 걸으면서 흔들리는 방향과 실제 회전을 **크기로** 가르는 값이다. 13번의 데드밴드로는 갈라지지 않는다 — 흔들림이 그 위로 올라오면 그대로 통과하고, 시간 상수로 걸러도 흔들림(1Hz 안팎)과 실제 회전의 시간 규모가 겹쳐 회전만 굼떠진다(400ms에서 ±5° 흔들림이 화면에 5.66° 남고 90° 회전은 2초 초과). 걸으면서 지도가 흔들리면 올리고, 고개를 조금 돌렸는데 반응하지 않으면 내린다
