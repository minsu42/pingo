## 2. 자동 검증 결과 (2026-07-29, 헤드리스 Chromium 149)

WebXR 기기가 없는 환경에서 확인 가능한 항목만 실행했다.

| 항목 | 결과 | 값 |
| --- | --- | --- |
| 페이지 로드·렌더 | 통과 | JS 오류 0건 |
| `http://127.0.0.1`의 `isSecureContext` | 통과 | `true` |
| `navigator.xr` 노출 | 통과 | 존재 |
| `isSessionSupported('immersive-ar')` | 통과(미지원 응답 정상 수신) | `false` |
| `isSessionSupported('inline')` | 통과 | `true` |
| 미지원 시 분기 | 통과 | 세션 시작 버튼 비활성화 + fallback 안내 로그 |

**여기서 확정된 것**: HTTPS 도메인 없이도 `localhost`/`127.0.0.1` 오리진은 secure context로 인정되어 `navigator.xr`이 노출된다. 운영 도메인·인증서가 미확정인 현재 상태에서도 실기기 검증을 진행할 수 있다는 뜻이다.

`immersive-ar`은 데스크톱 Chromium에서 원래 미지원이므로 위 `false`는 정상 결과이고, **지원 여부에 대한 판단 근거가 아니다.**

## 3. 실기기 검증

1~3차 검증을 2026-07-30에 수행했다. 결과는 3.3 체크리스트에 반영했고, 확인되지 않은 항목은 `미검증`·`부분 확인`으로 남겼다.

### 3.0 검증 요약

#### 1차 — 세션과 pose 수집

**`immersive-ar`이 동작한다.** Android Chrome 150과 삼성 인터넷 30 모두 `isSessionSupported('immersive-ar')`가 `true`였고, Chrome에서 세션·reference space·pose 수집이 모두 성공했다. 66.6초 세션 동안 추적이 유지됐다.

| 지표 | 실측값 |
| --- | --- |
| reference space | `local` (첫 후보에서 성공) |
| 프레임레이트 | 29.6fps |
| pose 없는 프레임 | 1.1% (1974 중 22) |
| 최대 이동 / 최대 회전 | 13.71m / 179.6° |

**확정 주기 기준이 실패했다.** 초안의 `2m 또는 15° 회전` 중 회전 조건이 상시 참이 되어, 확정 38회 중 30회가 회전으로 발화하고 63%가 최소 간격 1초에 걸려 나갔다. 회전량 중앙값은 23.5°였다. 규칙이 "1초마다 갱신"으로 퇴화해 `기술_의사결정_정리.md` 11.4에서 회전 트리거를 제거했다.

**오류 `name`만으로는 실패 원인을 특정할 수 없다.** 권한 거부가 `NotAllowedError`가 아니라 **`NotSupportedError`** 로 나타났다. 이름이 원인을 지시하지 않으므로 단독 판별 근거로 쓸 수 없다. 미지원 기기는 확보하지 못해 그쪽 오류 이름은 확인하지 못했다. 대신 실패까지 걸린 시간이 뚜렷하게 갈렸다.

| 상황 | 요청 → 실패 |
| --- | --- |
| 차단 상태에서 재시도 (2회 관측) | 10ms |
| 프롬프트가 뜬 뒤 거부 | 2.14초 |
| 프롬프트가 뜬 뒤 응답 지연 | 25.29초 |
| 프롬프트가 뜬 뒤 허용(성공) | 2.04초 |

**권한 거부는 앱에서 복구할 수 없다.** 한 번 거부한 뒤에는 프롬프트 없이 즉시 실패한다. 삼성 인터넷에서 권한 초기화 경로를 찾지 못했고 시크릿 모드로도 복구되지 않았다(원인 미상). 이 결과로 11.7 fallback과 권한 요청 시점 정책을 바꿨다.

**1차에서 확인하지 못한 것**: 좌표계 방향성(16번)과 층 전환(17~19번)이다. 검증 페이지가 `Δx`·`Δz`·`ΔY`를 로그에 남기지 않아 판정할 데이터가 없었다. 페이지를 수정하고 2차 검증에서 확인했다.

#### 2차 — 좌표계, 층 전환, 카메라 권한

**전방은 `-Z`가 맞다.** 약 28.7m 직진 구간에서 `Δz`가 단조 감소했다(`-1.58 → -3.59 → … → -28.57`). 좌표 스펙 8.3의 "`dZ` 부호 반전 없음" 전제가 실측으로 확인됐다.

**왕복 폐합 오차가 작다.** 28.7m를 가서 같은 경로로 돌아온 뒤 앵커로부터 `0.76m`였다. 총 이동 약 57m 대비 1.3%다. 다만 폐합 오차는 **누적 드리프트의 상한**만 보여준다. 왕복에서 드리프트가 상쇄될 수 있으므로 중간 경로의 정확도를 보장하지 않는다.

**층 전환이 ΔY로 뚜렷하게 갈린다.** 잡음 대비 25배 차이다.

| 구간 | ΔY |
| --- | --- |
| 평지 28m 직진 | `-0.13` ~ `+0.07` |
| 정지 상태 지터 (1~2초 간격 연속 기록) | 0.01 ~ 0.03m |
| 계단 한 층 상승 | `0 → 0.58 → 1.82 → 2.56 → 3.80` |
| 하강해 원위치 복귀 후 | `0.135` |

층고 `3.8m`는 **테스트 환경 값이며 역삼역 기준이 아니다.** 역삼역은 계단마다 높이가 다르므로 이 값을 임계값 근거로 쓰지 않는다. 이번 검증이 뒷받침하는 것은 잡음 바닥이 `±0.15m`로 낮고 상승·하강이 상쇄돼 누적되지 않는다는 점이며, 따라서 낮은 임계값(1m 수준)을 써도 오탐이 나지 않는다는 것이다. 층 확정은 11.2대로 경로 단계와 위치 재인식이 한다.

**`getUserMedia` 미리보기와 XR 세션은 공존하지 못한다.** 미리보기를 켠 채 세션을 열면 세션·reference space·dom-overlay가 모두 성공하는데 `getViewerPose`가 35프레임 전부 `null`이었고 카메라 화면도 검은 상태였다. 카메라 트랙은 세션 중에도 `readyState: live`로 남아 자동 반납되지 않았다. **오류 없이 조용히 실패하므로** 로그 없이는 기기 미지원으로 오진하기 쉽다.

**AR 동의와 `camera-access` 동의는 별개이며, 각각 origin에 저장된다.**

| 요청 | 상태 | 소요 | 프롬프트 |
| --- | --- | --- | --- |
| `dom-overlay`만 | 권한 초기화 직후 | 1625ms | 떴음 |
| `dom-overlay` + `camera-access` | 위 동의 10초 뒤, 같은 페이지 로드 | 1729ms | **또 떴음** |
| `dom-overlay` + `camera-access` | 둘 다 허용 후 새로고침 | 185ms | 뜨지 않음 |

같은 페이지 로드에서 AR 동의를 받은 직후에도 `camera-access`가 다시 물었으므로 두 동의는 별개다. 새로고침 후 프롬프트가 없었으므로 둘 다 origin에 저장된다. 따라서 사용자는 **앱 최초 1회만 두 프롬프트를 연속으로** 본다.

**`camera-access`가 부여된다.** `enabledFeatures`에 `["local", "camera-access", "viewer", "dom-overlay"]`가 모두 들어왔고 `XRView.camera`(895×1920)와 `getCameraImage`가 성공했다. 세션을 유지한 채 VPS 프레임을 확보할 수 있다. 다만 **확인된 것은 GPU 텍스처 획득까지다.** 픽셀 리드백·인코딩·전송 경로의 성능은 측정하지 않았다.

**`permissions.query({name: 'xr-spatial-tracking'})`는 쓸 수 없다.** Chrome 150이 이 이름을 `PermissionName`으로 받지 않아 `TypeError`가 난다. AR 동의 상태를 미리 조회할 수 없으므로, 세션을 열기 전 안내는 상태와 무관하게 표시해야 한다.

**추적 준비 시간이 있다.** `requestReferenceSpace` 성공부터 첫 pose까지 0.96 ~ 1.54초가 걸렸다. 이 구간의 `getViewerPose`는 `null`이며, 세션 종료 요약의 `posesMissing` 대부분이 여기서 발생한다. 추적이 잡힌 뒤에는 안정적이다.

#### 3차 — 측면 축과 엘리베이터

**측면 축에 거울 관계가 없다.** 앵커 방향으로 약 26m 직진한 뒤 **오른쪽으로 90°**(`dYawDeg 88.3`) 돌아 다시 직진했다.

| 시점 | Δx | Δz |
| --- | --- | --- |
| 회전 직전 | `-1.80` | `-26.47` |
| 회전 후 직진 종료 | **`+7.79`** | `-29.52` |

오른쪽 회전 후 전진이 `Δx` **양수** 방향으로 약 9.6m 이동했다. 3.4 4단계의 기대(`Δx` 양수)와 일치하므로 **8.3의 거울 보정은 적용하지 않는다.** 이로써 좌표 변환식의 축·부호가 모두 확정됐다.

**엘리베이터에서 추적이 무너진다.** 2개 층을 올라가며 측정했다.

| 지표 | 계단 (2차) | 엘리베이터 (3차) |
| --- | --- | --- |
| pose 결손률 | 1.7% (3628 중 61) | **19.5%** (1701 중 331) |
| 최장 연속 결손 | 약 1초 (1회) | **약 7초** |
| 도착 시점 ΔY | — | `3.98` |
| 내린 뒤 ΔY | — | `2.81` ~ `3.04` (안정되지 않음) |
| 층수 | 1개 층 | 2개 층 |
| 관측 ΔY | `3.80` | `2.81` ~ `3.04`, 최대 `4.20` |

**ΔY가 단조 증가하지 않는다.** 상승 중 궤적은 다음과 같았다.

```
1.03  상승 감지
 ↓    약 7초간 pose 없음
0.12  올라간 양을 통째로 되돌림
0.07
2.62
4.06  과대
3.98  도착·문 열리기 전
 ↓    다시 pose 없음
2.82  다시 깎임
2.81  내린 뒤
```

시각 특징을 잃고 IMU만으로 버티다가, 특징을 되찾을 때마다 추정치를 갈아엎는 패턴이다. 계단의 `0 → 0.58 → 1.82 → 2.56 → 3.80`과 대비된다.

**크기를 절반 이하로 본다.** 내린 뒤 값이 `2.81` ~ `3.04m`에서 안정되지 않았고 최대값도 `maxUpM 4.20m`이었다.

| 실제 층고 가정 | 2개 층 | 관측 대비 |
| --- | --- | --- |
| 계단 실측값 3.8m (같은 건물로 가정) | 7.6m | **37 ~ 40%** |
| 일반적인 최소 층고 3.0m | 6.0m | **47 ~ 51%** |

층고를 보수적으로 낮게 잡아도 절반 수준이다. 상승했다는 **방향은 맞았지만 크기는 쓸 수 없다.**

**단, 실패가 감지된다.** 7초간 pose가 전혀 나오지 않으므로 추적 상실을 명확히 알 수 있다. 또한 pose가 없으면 위치 확정 자체가 나가지 않아(확정 #6의 `afterMs`가 `8746`), 앱은 자연히 위치 갱신을 멈춘다. 다만 **blackout 사이에 반환된 pose는 값이 틀렸으므로**("pose가 있으면 믿는다"로는 부족하다) 엘리베이터 구간에서는 ΔY를 아예 쓰지 않아야 한다.

### 3.2 접속 방법

secure context가 필요하다. LAN IP + http로는 `navigator.xr`이 노출되지 않는다.

```text
https://i15a206.p.ssafy.io/webxr-probe.html
```

폰에서 LTE로 접속하면 되고, PC와 같은 네트워크에 있을 필요가 없다.

**대안 — 같은 Wi-Fi + Chrome 플래그 (배포 없이, 케이블 없이)**

2차 검증에서 쓴 방법이다. LAN IP + http는 secure context가 아니지만, Chrome에는 특정 origin만 secure context로 취급하는 개발용 플래그가 있다.

```bash
cd frontend && npm run dev:host   # LAN IP로 접속하려면 0.0.0.0 바인딩이 필요하다
```

폰 Chrome에서 `chrome://flags`를 열고 `insecure`로 검색해 **Insecure origins treated as secure**에 `http://<PC의 LAN IP>:5173`을 넣고 Enabled로 바꾼 뒤 Relaunch한다. 1장 실행 환경의 `isSecureContext`가 `true`면 적용된 것이다. 검증이 끝나면 Disabled로 되돌린다.

`chrome://flags`는 Chrome 전용이다. 삼성 인터넷에는 이 경로가 없어 이 방법을 쓸 수 없다.

이 방식은 페이지를 **불러올 때만** 네트워크가 필요하다. 로드된 뒤에는 pose 추적이 전부 기기 안에서 도므로 Wi-Fi가 끊겨도 진행 중인 세션은 유지된다. 다만 새로고침은 불가능해진다.

**대안 — USB 터널 (배포 없이 로컬에서)**

`adb reverse`는 USB 위로 터널을 만들기 때문에 네트워크가 필요 없다. dev 서버는 IPv4에도 바인딩해야 한다. Vite 기본값(`host: localhost`)은 Windows에서 `::1`만 열려 `adb`가 연결하는 `127.0.0.1`에 아무것도 없게 된다.

```bash
cd frontend && npm run dev:host
adb devices
adb reverse tcp:5173 tcp:5173
# 폰에서 http://localhost:5173/webxr-probe.html
```

### 3.4 좌표 정렬 검증 방법 (16번)

확인할 것은 **"XR 평면과 지도 평면의 방향성이 같은가"** 한 가지다. 거리의 절대값 비교로는 판별되지 않으므로 부호 조합을 본다.

`local` 공간의 방향은 세션을 시작한 순간으로 고정된다. 따라서 "앞으로 걸으면 `z`가 준다"는 세션 시작 방향으로 걸을 때만 성립한다. 아래 절차는 그 기준을 지킨다.

각 지점에서 AR 화면 하단의 **`지금 값 기록`** 버튼을 누르면 그 시점의 `Δx`·`Δz`·`ΔY`가 로그에 남는다. 화면 숫자를 옮겨 적을 필요가 없다.

1. 통로에서 진행 방향을 향한 채 세션을 시작한다. 이 방향을 A라 하고 기록한다.
2. A 방향으로 직선 5m 걷고 `지금 값 기록`을 누른다. 기대: `Δz ≈ -5`, `Δx ≈ 0`
3. 앵커 지점으로 돌아와 `지금 값 기록`을 누른다. 기대: 두 값 모두 0 근처
4. 오른쪽으로 90° 돌아 5m 걷고 `지금 값 기록`을 누른다. 기대: `Δx ≈ +5`, `Δz ≈ 0`
5. 4단계에서 `Δx`가 음수로 나오면 두 프레임의 방향성 가정이 틀린 것이다. 8.3 하단의 거울 보정(반사 후 회전 산출 + `dZ` 반전)을 적용하고 그 결과를 문서에 반영한다. `sinA` 부호만 뒤집는 것으로는 맞지 않는다.

**2차 검증 결과**

| 구간 | Δx | Δz | 기대와 일치 |
| --- | --- | --- | --- |
| A 방향 직진 (5m 대신 약 28.7m) | `-2.28` | `-28.57` | 일치. 전방이 `-Z` |
| 같은 경로로 앵커 복귀 | `-0.58` | `+0.50` | 일치. 폐합 오차 0.76m |
| 오른쪽 90° 후 직진 (3차, 약 9.6m) | `-1.80 → +7.79` | `-26.47 → -29.52` | 일치. `Δx` 양수 |

**축·부호가 모두 확정됐다.** 전방은 `-Z`이고, 오른쪽 회전 후 전진은 `Δx` 양수다. 3차 검증에서 회전량 `dYawDeg 88.3`이 기록됐고 이후 `Δx`가 약 9.6m 증가했다. 5단계의 거울 보정은 **적용하지 않는다.**

직진 구간에서 `Δx`가 `-2.28`까지 벌어졌다가 복귀 시 `-0.58`로 돌아온 것은, 그 편차 대부분이 누적 드리프트가 아니라 실제 보행 경로의 휘어짐이었음을 시사한다. 순수 드리프트라면 왕복에서 상쇄되지 않는다.

### 3.5 카메라 권한과 표시 방식 (20~24번)

두 가지를 한 번에 확인한다. 검증 페이지 5장에서 `카메라 미리보기 시작`을 누른 뒤 세션을 시작하면 된다.

**(가) AR 세션 동의가 카메라 권한으로 갈음되는가 — 20번**

앱은 초기 진입 직후 카메라를 허용받으므로(`화면_흐름도.md` 5.2), 경로 안내 화면에서 세션을 열 때 프롬프트가 또 뜨는지가 UI 흐름을 좌우한다.

소요 시간은 로그의 `elapsedMs`로 남지만 **확정 판단은 화면에 프롬프트가 실제로 떴는지로 한다.** 시간은 보조 지표다.

**결과 — 갈음되지 않는다.** 카메라를 허용해 미리보기가 나오는 상태에서 세션을 열었는데 "주변 환경의 3D 지도를 생성하고 카메라 위치를 추적" 프롬프트가 떴다. 카메라 권한과 AR 동의는 별개다.

이어서 `camera-access`를 켜고 끄며 비교해 **AR 동의와 `camera-access` 동의도 서로 별개**임을 확인했다. 권한을 초기화한 뒤 측정한 값이다.

| 요청 `optionalFeatures` | 조건 | 소요 | 프롬프트 |
| --- | --- | --- | --- |
| `["dom-overlay"]` | 권한 초기화 직후 | 1625ms | 떴음 |
| `["dom-overlay","camera-access"]` | 위 동의 10초 뒤, 같은 페이지 로드 | 1729ms | **또 떴음** |
| `["dom-overlay","camera-access"]` | 둘 다 허용 후 새로고침 | 185ms | 뜨지 않음 |

세 번째 행이 두 동의 모두 origin에 저장됨을 보여준다. 프롬프트가 뜬 경우 1.6초 이상, 뜨지 않은 경우 200ms 미만으로 갈렸으나, 앞선 값은 사용자가 탭하는 속도에 달렸으므로 시간은 보조 지표로만 쓴다.

**UI 영향**: 경로 안내에 처음 들어가는 사용자는 시스템 프롬프트를 **연속 두 번** 본다. 세션 도중에는 기능을 추가할 수 없어 `camera-access`를 처음부터 함께 요청해야 하므로 두 프롬프트를 하나로 줄일 수 없다. 또한 `permissions.query`로 동의 상태를 미리 알 수 없으므로(체크리스트 24번), 앱이 먼저 표시할 안내는 상태와 무관하게 항상 띄워야 한다.

**(나) 카메라를 `<video>`로 띄운 채 세션이 유지되는가 — 21·22번**

FR-U-010은 `상단 카메라 · 하단 지도` 구조를 요구하는데, `immersive-ar` 세션은 화면 전체를 XR 컴포지터가 그린다. 따라서 구현 방식이 둘로 갈린다.

| 방식 | 성립 조건 | 결과 |
| --- | --- | --- |
| (a) dom-overlay | 세션이 카메라를 그리고 지도·안내 UI를 DOM 오버레이로 얹는다 | **가능** |
| (b) video + pose | `getUserMedia` 미리보기로 카메라를 표시하고 XR 세션은 pose만 쓴다 | **불가능** |

**(b)는 성립하지 않는다.** 미리보기를 켠 채 세션을 열면 세션 시작·`XRWebGLLayer`·`requestReferenceSpace`·`dom-overlay`가 전부 성공하는데 `getViewerPose`만 35프레임 내내 `null`이었고, 카메라 화면도 검은 상태였다. 미리보기를 끄고 같은 조작을 하면 즉시 정상 동작한다.

카메라 트랙은 세션 중에도 `readyState: live`, `muted: false`로 남았다. 즉 브라우저가 트랙을 죽여 알려주는 것이 아니라, 카메라를 잡고 있는 쪽이 우선권을 갖고 ARCore가 조용히 굶는다.

**실패가 오류로 드러나지 않는다는 점이 위험하다.** 예외도 없고 세션도 열려 있어, 로그 없이 보면 기기가 WebXR을 지원하지 않는 것으로 오진하기 쉽다.

**구현 규칙**: `requestSession` 전에 모든 `getUserMedia` 카메라 트랙을 `stop()` 해야 한다. 초기 권한 화면은 이미 `stopMediaStream`으로 정리하고 있다(`frontend/src/features/permissions/model/permission.service.ts`). 카메라를 켜는 화면이 추가될 때 같은 처리가 빠지지 않도록 `frontend/AGENTS.md`에 규칙으로 남긴다.

**U-10 레이아웃은 (a)로 간다.** 카메라 영상은 XR 세션이 직접 그리고, 2D 지도와 안내 UI는 `dom-overlay`(`type: screen`)에 얹는다. S15P11A206-141의 구현 방식도 이 전제를 따른다.

### 3.6 실패 조건 기록란

미지원·권한 거부·세션 실패를 구분하려면 실제 오류 `name`이 필요하다. 페이지가 `name`과 `message`를 그대로 로그에 남기므로 아래에 옮겨 적는다. **예상값을 미리 채워두지 않는다.**

| 조건 | 재현 방법 | 실제 오류 `name` | 관찰된 동작 |
| --- | --- | --- | --- |
| 카메라 권한 거부 | 프롬프트에서 거부 | `NotSupportedError` | 메시지 `The specified session configuration is not supported.` 요청 후 2.14초 만에 실패 |
| 권한 거부 후 재시도 | 거부 상태에서 다시 시작 | `NotSupportedError` | **프롬프트 없이 10ms 만에 실패.** 2회 반복 동일. 앱에서 복구 불가 |
| 권한 초기화 시도 | 브라우저 설정·시크릿 모드 | — | 삼성 인터넷 30에서 권한 초기화 경로를 찾지 못했고 시크릿 모드로도 복구되지 않음 (원인 미상) |
| ARCore 미설치·미지원 기기 | 해당 기기로 접속 | (미기록) | 해당 기기를 확보하지 못함 |
| secure context 아님 | LAN IP + http로 접속 | (해당 없음) | `isSecureContext`가 `false`로 표시됐다. 세션 시작은 시도하지 않았다. Chrome 플래그로 해제된다(3.2) |
| `getUserMedia` 미리보기 + 세션 | 미리보기를 켠 채 세션 시작 | (오류 없음) | 세션은 열리나 `getViewerPose`가 전부 `null`. 3.5 참고 |
| `camera-access` 미요청 | `optionalFeatures`에서 제외 | (오류 없음) | 세션은 열리나 `XRView.camera`가 없다 |
| 세션 중 앱 전환·화면 잠금 | 홈 버튼 후 복귀 | (미기록) | |
| iOS Safari | iPhone에서 접속 | (미기록) | |

**`NotSupportedError`는 원인을 특정하지 못한다.** 권한 거부에서도 이 이름이 나왔다. 판별 기준은 `기술_의사결정_정리.md` 11.7을 따른다.

## 4. 현재 시점 결론

**확정된 것**

- **실기기에서 `immersive-ar` 세션과 pose 수집이 된다.** WebXR 기반 상대 위치 추적의 기술적 전제가 충족됐다.
- reference space는 `local`로 확보된다. 프레임레이트 29.6fps, pose 없는 프레임 1.1%로 66초간 추적이 유지됐다.
- 배포된 HTTPS 주소로 실기기 검증이 가능하다. 같은 네트워크나 adb가 필요하지 않다. 같은 Wi-Fi + Chrome 플래그도 쓸 수 있다(3.2).
- 확정 주기에서 회전 트리거는 쓸 수 없다(11.4 개정). 개정 후 규칙은 실측에서 적합했다.
- 실패 원인 판별은 오류 `name`이 아니라 `isSessionSupported`와 실패 소요 시간으로 한다(11.7 개정).
- 권한 거부는 앱에서 되돌릴 수 없다. 권한 요청 시점 정책이 이 결과로 바뀌었다(11.7).
- **좌표 변환식의 축·부호가 확정됐다.** 전방은 `-Z`이고 오른쪽 회전 후 전진은 `Δx` 양수다. 거울 보정은 적용하지 않는다.
- **엘리베이터에서는 추적을 신뢰할 수 없다.** 결손 19.5%, 7초 연속 결손, ΔY가 실제 상승의 절반 이하였다. 다만 실패가 pose 부재로 드러나 감지는 가능하다.
- **드리프트가 작다.** 약 57m 왕복에서 폐합 오차 0.76m(1.3%), 수직 0.135m다. 상한값이지만 재인식 간격을 잡는 근거로 쓸 수 있다.
- **층 전환은 ΔY로 감지할 수 있다.** 평지 잡음이 `±0.15m`로 낮아 1m 수준의 낮은 임계값에서도 오탐이 나지 않는다. 층 확정은 여전히 경로 단계와 재인식이 한다(11.2).
- **`camera-access`가 부여된다.** 세션을 유지한 채 VPS 프레임을 확보할 수 있어, 경로 안내 중 주기적 재인식 설계가 성립한다.
- **`getUserMedia`와 XR 세션은 공존하지 못한다.** 카메라 표시는 XR 세션이 맡고 지도는 `dom-overlay`로 얹는다(3.5).
- **AR 동의와 `camera-access` 동의는 각각 별개이며 origin에 저장된다.** 사용자는 앱 최초 1회만 프롬프트 두 개를 본다.
- **AR 동의 상태는 미리 조회할 수 없다.** 세션 전 안내는 항상 표시해야 한다.

**확정하지 못한 것**

- **에스컬레이터에서의 추적**(19번의 나머지). 엘리베이터 결과로 보아 저하가 예상되나 실측하지 않았다.
- 계단 ΔY와 **역삼역 실제 층고**의 대조. 측정한 `3.8m`는 테스트 환경 값이다.
- 회전의 **정확도**. 변화가 관측된다는 것만 확인했고 실제 각도 대비 오차는 측정하지 않았다.
- `getCameraImage`로 얻은 텍스처를 **픽셀로 읽어 백엔드로 보내는 경로의 성능**. 텍스처 획득까지만 확인했다.
- 검증 기기 모델·Android 버전·ARCore 버전.

`forwardMap` 출처는 검증이 아니라 계약 문제였고 **2026-07-31 AI·BE 협의로 확정**됐다. 위치 인식 응답에 캐노니컬 수평면 2D 단위벡터를 추가한다(`역삼역_FE_좌표연동_스펙.md` 8.5).

**S15P11A206-295 이후 착수 판단**

FR-U-010의 기술적 전제가 모두 확인됐으므로 착수할 수 있다. 좌표 변환식의 축·부호까지 확정돼 구현에 필요한 계약이 갖춰졌다. 남은 항목 중 착수를 막는 것은 없다. 에스컬레이터는 미검증이지만 보수적으로 신뢰 구간에서 제외해 두었으므로, 실측 결과가 나오면 제외를 해제하는 방향으로만 바뀐다.

**S15P11A206-296 착수 판단**: 좌표 변환의 축·부호가 실측으로 확정되고 `forwardMap` 계약도 합의됐으므로 착수할 수 있다. BE 구현이 아직 없어 방향 값은 목업으로 두고 주입 지점을 분리한다.
