## 2. 자동 검증 결과 (2026-07-29, 헤드리스 Chromium 149)

WebXR 기기가 없는 환경에서 확인 가능한 항목만 실행했다.

| 항목 | 결과 | 값 |
| --- | --- | --- |
| 페이지 로드·렌더 | 통과 | JS 오류 0건 |
| `http://127.0.0.1`의 `isSecureContext` | 통과 | `true` |
| `navigator.xr` 노출 | 통과 | 존재 |
| `isSessionSupported('immersive-ar')` | 통과(미지원 응답 정상 수신) | `false` |
| `isSessionSupported('inline')` | 통과 | `true` |
| 미지원 시 분기 | 통과 | 세션 시작 버튼 비활성화 + fallback 안내 로그 |

**여기서 확정된 것**: HTTPS 도메인 없이도 `localhost`/`127.0.0.1` 오리진은 secure context로 인정되어 `navigator.xr`이 노출된다. 운영 도메인·인증서가 미확정인 현재 상태에서도 실기기 검증을 진행할 수 있다는 뜻이다.

`immersive-ar`은 데스크톱 Chromium에서 원래 미지원이므로 위 `false`는 정상 결과이고, **지원 여부에 대한 판단 근거가 아니다.**

## 3. 실기기 검증

1차 검증을 2026-07-30에 수행했다. 결과는 3.3 체크리스트에 반영했고, 확인되지 않은 항목은 `미검증`으로 남겼다.

### 3.0 1차 검증 요약

**`immersive-ar`이 동작한다.** Android Chrome 150과 삼성 인터넷 30 모두 `isSessionSupported('immersive-ar')`가 `true`였고, Chrome에서 세션·reference space·pose 수집이 모두 성공했다. 66.6초 세션 동안 추적이 유지됐다.

| 지표 | 실측값 |
| --- | --- |
| reference space | `local` (첫 후보에서 성공) |
| 프레임레이트 | 29.6fps |
| pose 없는 프레임 | 1.1% (1974 중 22) |
| 최대 이동 / 최대 회전 | 13.71m / 179.6° |

**확정 주기 기준이 실패했다.** 초안의 `2m 또는 15° 회전` 중 회전 조건이 상시 참이 되어, 확정 38회 중 30회가 회전으로 발화하고 63%가 최소 간격 1초에 걸려 나갔다. 회전량 중앙값은 23.5°였다. 규칙이 "1초마다 갱신"으로 퇴화해 `기술_의사결정_정리.md` 11.4에서 회전 트리거를 제거했다.

**오류 `name`만으로는 실패 원인을 특정할 수 없다.** 권한 거부가 `NotAllowedError`가 아니라 **`NotSupportedError`** 로 나타났다. 이름이 원인을 지시하지 않으므로 단독 판별 근거로 쓸 수 없다. 미지원 기기는 확보하지 못해 그쪽 오류 이름은 확인하지 못했다. 대신 실패까지 걸린 시간이 뚜렷하게 갈렸다.

| 상황 | 요청 → 실패 |
| --- | --- |
| 차단 상태에서 재시도 (2회 관측) | 10ms |
| 프롬프트가 뜬 뒤 거부 | 2.14초 |
| 프롬프트가 뜬 뒤 응답 지연 | 25.29초 |
| 프롬프트가 뜬 뒤 허용(성공) | 2.04초 |

**권한 거부는 앱에서 복구할 수 없다.** 한 번 거부한 뒤에는 프롬프트 없이 즉시 실패한다. 삼성 인터넷에서 권한 초기화 경로를 찾지 못했고 시크릿 모드로도 복구되지 않았다(원인 미상). 이 결과로 11.7 fallback과 권한 요청 시점 정책을 바꿨다.

**1차에서 확인하지 못한 것**: 좌표계 방향성(16번)과 층 전환(17~19번)이다. 검증 페이지가 `Δx`·`Δz`·`ΔY`를 로그에 남기지 않아 판정할 데이터가 없었다. 페이지를 수정하고 2차 검증에서 확인한다.

### 3.2 접속 방법

secure context가 필요하다. LAN IP + http로는 `navigator.xr`이 노출되지 않는다.

**권장 — 배포된 HTTPS 주소 (Wi-Fi·adb 불필요)**

`develop`에 merge하면 Jenkins가 자동으로 빌드·배포한다. Webhook은 모든 브랜치에서 발생하지만 Pipeline은 `develop`을 checkout하므로(`Jenkins_CI_설정.md` 37행) feature 브랜치 코드가 운영에 올라가지 않는다.

```text
https://i15a206.p.ssafy.io/webxr-probe.html
```

폰에서 LTE로 접속하면 되고, PC와 같은 네트워크에 있을 필요가 없다.

**대안 — USB 터널 (배포 없이 로컬에서)**

`adb reverse`는 USB 위로 터널을 만들기 때문에 네트워크가 필요 없다. dev 서버는 IPv4에도 바인딩해야 한다. Vite 기본값(`host: localhost`)은 Windows에서 `::1`만 열려 `adb`가 연결하는 `127.0.0.1`에 아무것도 없게 된다.

```bash
cd frontend && npm run dev:host
adb devices
adb reverse tcp:5173 tcp:5173
# 폰에서 http://localhost:5173/webxr-probe.html
```

17~19번은 층 전환 구간을 다룬다. 이 구간은 WebXR 추적이 가장 취약하다.

- **에스컬레이터**: 사용자는 서 있는데 주변 시각 특징이 함께 움직인다. ARCore가 이를 이동으로 인식하는지, 추적이 깨지는지 확인한다.
- **엘리베이터**: 밀폐 공간, 시각 특징 부족, 수직 가속이 겹친다. 추적 실패 가능성이 가장 높다.

층 전환 전후로 `지금 값 기록`을 눌러 `ΔY`를 남기고, 세션 종료 요약의 `maxUpM`·`maxDownM`과 함께 실제 층고와 비교한다.

추적이 끊기는 구간이 확인되면 `기술_의사결정_정리.md` 11.7 fallback 표에 해당 조건을 추가하고, 그 구간은 "추적 중단 → 도착 후 재인식 유도"로 처리한다.

### 3.4 좌표 정렬 검증 방법 (16번)

확인할 것은 **"XR 평면과 지도 평면의 방향성이 같은가"** 한 가지다. 거리의 절대값 비교로는 판별되지 않으므로 부호 조합을 본다.

`local` 공간의 방향은 세션을 시작한 순간으로 고정된다. 따라서 "앞으로 걸으면 `z`가 준다"는 세션 시작 방향으로 걸을 때만 성립한다. 아래 절차는 그 기준을 지킨다.

각 지점에서 AR 화면 하단의 **`지금 값 기록`** 버튼을 누르면 그 시점의 `Δx`·`Δz`·`ΔY`가 로그에 남는다. 화면 숫자를 옮겨 적을 필요가 없다.

1. 통로에서 진행 방향을 향한 채 세션을 시작한다. 이 방향을 A라 하고 기록한다.
2. A 방향으로 직선 5m 걷고 `지금 값 기록`을 누른다. 기대: `Δz ≈ -5`, `Δx ≈ 0`
3. 앵커 지점으로 돌아와 `지금 값 기록`을 누른다. 기대: 두 값 모두 0 근처
4. 오른쪽으로 90° 돌아 5m 걷고 `지금 값 기록`을 누른다. 기대: `Δx ≈ +5`, `Δz ≈ 0`
5. 4단계에서 `Δx`가 음수로 나오면 두 프레임의 방향성 가정이 틀린 것이다. 8.3 하단의 거울 보정(반사 후 회전 산출 + `dZ` 반전)을 적용하고 그 결과를 문서에 반영한다. `sinA` 부호만 뒤집는 것으로는 맞지 않는다.

| 구간 | Δx | Δz | 기대와 일치 |
| --- | --- | --- | --- |
| A 방향 5m | | | |
| 오른쪽 90° 후 5m | | | |

### 3.5 실패 조건 기록란

미지원·권한 거부·세션 실패를 구분하려면 실제 오류 `name`이 필요하다. 페이지가 `name`과 `message`를 그대로 로그에 남기므로 아래에 옮겨 적는다. **예상값을 미리 채워두지 않는다.**

| 조건 | 재현 방법 | 실제 오류 `name` | 관찰된 동작 |
| --- | --- | --- | --- |
| 카메라 권한 거부 | 프롬프트에서 거부 | `NotSupportedError` | 메시지 `The specified session configuration is not supported.` 요청 후 2.14초 만에 실패 |
| 권한 거부 후 재시도 | 거부 상태에서 다시 시작 | `NotSupportedError` | **프롬프트 없이 10ms 만에 실패.** 2회 반복 동일. 앱에서 복구 불가 |
| 권한 초기화 시도 | 브라우저 설정·시크릿 모드 | — | 삼성 인터넷 30에서 권한 초기화 경로를 찾지 못했고 시크릿 모드로도 복구되지 않음 (원인 미상) |
| ARCore 미설치·미지원 기기 | 해당 기기로 접속 | (미기록) | 해당 기기를 확보하지 못함 |
| secure context 아님 | LAN IP + http로 접속 | (미기록) | |
| 세션 중 앱 전환·화면 잠금 | 홈 버튼 후 복귀 | (미기록) | |
| iOS Safari | iPhone에서 접속 | (미기록) | |

**`NotSupportedError`는 원인을 특정하지 못한다.** 권한 거부에서도 이 이름이 나왔다. 판별 기준은 `기술_의사결정_정리.md` 11.7을 따른다.

## 4. 현재 시점 결론

**확정된 것**

- **실기기에서 `immersive-ar` 세션과 pose 수집이 된다.** WebXR 기반 상대 위치 추적의 기술적 전제가 충족됐다.
- reference space는 `local`로 확보된다. 프레임레이트 29.6fps, pose 없는 프레임 1.1%로 66초간 추적이 유지됐다.
- 배포된 HTTPS 주소로 실기기 검증이 가능하다. 같은 네트워크나 adb가 필요하지 않다.
- 확정 주기에서 회전 트리거는 쓸 수 없다(11.4 개정).
- 실패 원인 판별은 오류 `name`이 아니라 `isSessionSupported`와 실패 소요 시간으로 한다(11.7 개정).
- 권한 거부는 앱에서 되돌릴 수 없다. 권한 요청 시점 정책이 이 결과로 바뀌었다(11.7).

**확정하지 못한 것**

- 좌표 변환식의 축·부호(체크리스트 16번). `Δx`·`Δz` 로그가 없어 2차 검증으로 넘겼다.
- 층 전환 구간의 추적 유지와 ΔY 정확도(17~19번).
