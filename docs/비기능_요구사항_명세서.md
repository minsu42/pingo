# 외국인 관광객 대상 지하철 실내 내비게이션 비기능 요구사항 명세서

## 1. 문서 목적

본 문서는 외국인 관광객 대상 지하철 실내 내비게이션 서비스의 비기능 요구사항을 정의한다.

비기능 요구사항은 서비스가 기능적으로 동작하는 것뿐만 아니라, 실제 사용 환경에서 안정적이고 안전하게 사용할 수 있도록 성능, 보안, 개인정보, 사용성, 접근성, 호환성, 운영 기준을 명확히 하기 위한 문서이다.

---

## 2. 비기능 요구사항 범위

본 문서는 다음 영역을 다룬다.

- 성능
- 사용성
- 접근성
- 호환성
- 보안
- 개인정보 보호
- WebRTC 통신 안정성
- VPS 및 위치 인식 안정성
- 데이터 관리
- 장애 대응
- 운영 및 모니터링
- 확장성

비기능 요구사항의 운영 책임은 `PinGo_역할분배_최종기획안_v4.md`를 따른다. HTTPS/WSS, STUN/TURN, Nginx reverse proxy, 배포·rollback, 외부망 WebRTC 연결 검증은 이정우가 책임진다. WebRTC signaling, 상담 상태, 재연결 로직, DataChannel 이벤트 의미 처리는 오서현이 책임진다.

| 우선순위 | 의미 |

## 4. 성능 요구사항

### NFR-P-001. 웹앱 초기 로딩 성능

| 항목 | 내용 |
| --- | --- |
| 설명 | 사용자는 웹앱에 빠르게 접속하고 언어 선택 화면을 볼 수 있어야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 사용자가 웹앱에 접속하면 초기 화면은 가능한 한 빠르게 표시되어야 한다.
- 모바일 네트워크 환경을 고려해 초기 로딩 리소스를 최소화해야 한다.
- 지도, 카메라, WebRTC 등 무거운 기능은 필요한 시점에 로드하는 것을 권장한다.

#### 목표 기준

- 일반적인 모바일 네트워크 환경에서 첫 화면은 3초 이내 표시를 목표로 한다.
- MVP 시연 환경에서는 첫 화면이 2초 이내 표시되는 것을 목표로 한다.

---

### NFR-P-002. 현재 역 후보 조회 성능

| 항목 | 내용 |
| --- | --- |
| 설명 | GPS 기반 현재 역 후보 조회는 사용자가 기다릴 수 있는 시간 안에 완료되어야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 위치 권한 허용 후 주변 역 후보를 빠르게 표시해야 한다.
- GPS가 느리거나 실패할 경우 직접 역 선택으로 전환할 수 있어야 한다.

#### 목표 기준

- 주변 역 후보 조회는 3초 이내 완료를 목표로 한다.
- 5초 이상 지연될 경우 직접 선택 안내를 표시한다.

---

### NFR-P-003. VPS 위치 인식 응답 시간

| 항목 | 내용 |
| --- | --- |
| 설명 | 카메라 기반 위치 인식은 사용자가 흐름을 잃지 않을 정도의 시간 안에 결과를 반환해야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 사용자가 위치 인식을 요청하면 진행 상태를 표시해야 한다.
- 위치 인식이 지연될 경우 재시도 또는 수동 선택을 제공해야 한다.
- 자체 VPS, 외부 VPS, QR/마커 인식 등 방식에 따라 응답 시간이 달라질 수 있으므로 공통 대기 기준을 둔다.

#### 목표 기준

- 위치 인식 결과는 5초 이내 반환을 목표로 한다.
- 8초 이상 지연될 경우 사용자에게 대체 흐름을 제공한다.

---

### NFR-P-004. 경로 탐색 성능

| 항목 | 내용 |
| --- | --- |
| 설명 | 실내 경로 탐색은 즉각적인 화면 전환이 가능할 정도로 빠르게 수행되어야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 현재 위치와 목적지가 확정되면 경로를 생성해야 한다.
- 빠른 경로, 계단 없는 경로, 엘리베이터 중심 경로를 제공해야 한다.

#### 목표 기준

- 경로 탐색 결과는 2초 이내 반환을 목표로 한다.
- MVP에서는 대상 역이 1개이므로 경로 그래프 규모를 작게 유지한다.

---

### NFR-P-005. 경로 안내 화면 성능

| 항목 | 내용 |
| --- | --- |
| 설명 | 카메라 화면과 지도 화면이 동시에 표시되어도 화면 조작이 끊기지 않아야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 경로 안내 화면은 상단 카메라와 하단 지도를 동시에 표시한다.
- 카메라 미리보기, 화살표 오버레이, 지도 표시가 사용자 조작을 방해하지 않아야 한다.
- 모바일 브라우저에서 과도한 배터리 소모와 발열을 줄이도록 불필요한 연산을 줄여야 한다.

#### 목표 기준

- MVP 시연 단말에서 경로 안내 화면이 눈에 띄는 끊김 없이 동작해야 한다.
- 지도 확대/축소, 상담 버튼 클릭, 위치 재인식 버튼 클릭이 정상 동작해야 한다.

## 5. 사용성 요구사항

### NFR-U-001. 비로그인 사용

| 항목 | 내용 |
| --- | --- |
| 설명 | 외국인 관광객은 회원가입 또는 로그인 없이 서비스를 이용할 수 있어야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 일반 사용자는 웹앱 접속 후 바로 서비스를 시작할 수 있어야 한다.
- 사용자에게 회원가입, 이메일 인증, 소셜 로그인 등을 요구하지 않는다.
- 상담자와 관리자는 별도 로그인한다.

#### 완료 기준

- 일반 사용자가 로그인 없이 언어 선택, 권한 요청, 역 선택, 위치 인식, 목적지 검색, 경로 안내를 사용할 수 있다.

---

### NFR-U-002. 짧고 명확한 안내 문구

| 항목 | 내용 |
| --- | --- |
| 설명 | 외국인 관광객이 빠르게 이해할 수 있도록 화면 문구는 짧고 명확해야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 안내 문구는 한 화면에서 너무 길지 않아야 한다.
- 사용자의 다음 행동이 명확해야 한다.
- 실패 상황에서는 원인보다 다음 행동을 우선 안내한다.

#### 예시

```text
주변을 천천히 비춰주세요.
위치를 찾지 못했어요. 다시 촬영하거나 지도에서 선택하세요.
출구에 도착하셨나요?
```

---

### NFR-U-003. 상담 접근성

| 항목 | 내용 |
| --- | --- |
| 설명 | 사용자는 길찾기 중 문제가 생겼을 때 쉽게 상담을 요청할 수 있어야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 상담 요청 버튼은 주요 사용자 화면에서 접근 가능해야 한다.
- 위치 인식 실패 화면에서는 상담 버튼을 강조 표시한다.
- 경로 안내 화면에서는 상담 버튼을 항상 노출한다.

#### 완료 기준

- 현재 역 확인, 위치 인식, 목적지 검색, 경로 안내, 출구 도착, 외부 지도 연계 화면에서 상담 요청 진입이 가능하다.

---

### NFR-U-004. 사용 흐름 복귀 가능성

| 항목 | 내용 |
| --- | --- |
| 설명 | 사용자가 중간에 실패하거나 상담을 종료해도 기존 길찾기 흐름으로 돌아갈 수 있어야 한다. |
| 우선순위 | 중요 |

#### 요구사항

- 상담 종료 후 기존 경로 안내로 복귀할 수 있어야 한다.
- 위치 인식 실패 후 수동 위치 선택으로 흐름을 이어갈 수 있어야 한다.
- 외부 지도 앱 연계 전까지 사용자가 목적지를 변경할 수 있어야 한다.

## 7. 호환성 요구사항

### NFR-C-001. 모바일 브라우저 호환성

| 항목 | 내용 |
| --- | --- |
| 설명 | 서비스는 별도 앱 설치 없이 모바일 웹 브라우저에서 동작해야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- Android Chrome에서 주요 기능이 동작해야 한다.
- iOS Safari에서 주요 화면 접근이 가능해야 한다.
- 브라우저별 카메라, 위치정보, 마이크 권한 정책 차이를 고려해야 한다.
- WebXR 상대 위치 추적은 지원 여부를 실행 시점에 탐지하고, 미지원 환경에서도 경로 안내가 동작해야 한다.

#### MVP 기준

- MVP 시연은 Android Chrome 기준으로 안정성을 확보한다.
- iOS Safari는 가능하면 주요 화면 접근과 기본 흐름을 확인한다.
- WebXR `immersive-ar`은 Android Chrome + ARCore 지원 기기를 기준으로 한다. iOS Safari는 `immersive-ar`을 지원하지 않으므로 추적 없이 위치 재인식·수동 위치 선택으로 안내한다. 이는 결함이 아니라 확정된 fallback이다.

### NFR-C-002. 반응형 화면

| 항목 | 내용 |
| --- | --- |
| 설명 | 다양한 모바일 화면 크기에서 주요 UI가 깨지지 않아야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 화면은 모바일 세로 모드를 우선 기준으로 설계한다.
- 카메라 상단, 지도 하단 구조가 작은 화면에서도 유지되어야 한다.
- 버튼과 안내 문구가 화면 밖으로 밀려나지 않아야 한다.

---

### NFR-C-003. 외부 지도 앱 연계 호환성

| 항목 | 내용 |
| --- | --- |
| 설명 | 네이버지도 연계가 앱 설치 여부와 관계없이 동작해야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- MVP에서는 네이버지도 연계를 우선 적용한다.
- 지도 앱이 설치되어 있지 않은 경우 웹 지도 링크로 연결한다.
- 외부 지도 연계 시 출발지는 사용자의 실제 GPS 위치를 사용한다.
- GPS 사용이 불가능하면 출구 위치를 출발지로 사용할지 확인한다.

## 8. 보안 요구사항

### NFR-S-001. HTTPS 적용

| 항목 | 내용 |
| --- | --- |
| 설명 | 위치정보, 카메라, 마이크, WebRTC를 사용하므로 서비스는 HTTPS 환경에서 제공되어야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 사용자 웹앱은 HTTPS에서 동작해야 한다.
- 상담자 페이지와 관리자 페이지도 HTTPS에서 동작해야 한다.
- 브라우저 권한 API와 WebRTC 사용을 위해 로컬 개발 환경을 제외하고 보안 연결을 사용한다.

---

### NFR-S-002. 권한 기반 접근 제어

| 항목 | 내용 |
| --- | --- |
| 설명 | 사용자, 상담자, 관리자 권한은 분리되어야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 일반 사용자는 관리자 또는 상담자 페이지에 접근할 수 없어야 한다.
- 상담자는 상담자 전용 페이지에만 접근해야 한다.
- 관리자는 관리자 페이지에 접근할 수 있어야 한다.
- 상담자는 자신에게 할당된 역 또는 상담 요청만 조회하도록 제한하는 것을 목표로 한다.

---

### NFR-S-003. 상담 세션 접근 제어

| 항목 | 내용 |
| --- | --- |
| 설명 | 상담 세션은 해당 사용자와 수락한 상담자만 접근할 수 있어야 한다. |
| 우선순위 | 필수 |

#### 요구사항

- 상담 세션 ID는 추측하기 어렵게 생성해야 한다.
- 상담자가 수락하지 않은 상담 세션에 접근할 수 없도록 제한해야 한다.
- 종료된 상담 세션은 재접속을 제한해야 한다.

## 18. 구현 중 검증할 사항

1. 실제 배포 도메인 확정
2. 네이버지도 URL Scheme 또는 웹 링크의 최종 형식 검증
3. 카메라 이미지 즉시 폐기 로그 검증
4. 관리자 데이터 백업 방식 검증

다음 항목은 확정된 기준으로 적용한다.

| 항목 | 확정 기준 |
| --- | --- |
| MVP 기준 브라우저 | Android Chrome |
| 대상 역 | 역삼역 |
| 배포 방식 | Nginx reverse proxy + HTTPS |
| HTTPS 인증서 | Let's Encrypt 기준 |
| WebRTC STUN/TURN | 무료 STUN 우선, 불안정 시 TURN 추가 |
| VPS 이미지 저장 | 기본 저장하지 않음, 처리 후 즉시 폐기 |
| 다국어 리소스 | MVP에서는 프론트엔드 리소스와 `nameKo`, `nameEn` 응답 병행 |
